# transaction-service: architect rulings on the contract

Status: **approved with the rulings below**, 2026-11-10. The contract under review is the backend's transaction-service contract v4. It covers four units: TRNL (COTRN00C), TRNV (COTRN01C), TRNA (COTRN02C) and RPTS (CORPT00C), plus DTCK (CSUTLDTC) as the library `LegacyDateCheck`.

TRNL, TRNV and RPTS may be coded now. TRNA may be coded now as well. Its ID allocation is already built in `ledger-core`, and the collision with daily-file IDs is settled in [batch.md](batch.md#transaction-ids-from-the-file-and-from-the-services). Backend writes these rulings into the contract as v5 before the first unit merges. A ruling here overrides the contract where the two differ. Two checks confirmed the item tables against the specs: TRNL 49 of 49, TRNV 32 of 32, TRNA 62 of 62 and RPTS 47 of 47. No table lists an ID the spec lacks. Add the count line "47 of 47" to RPTS.

## 1. Rulings for every unit

### Access and the card number reveal (D-09)

DEF-TRNV-004 is a D-09 item, and the ledger has it as `fixed`. "Fixed" means the whole fix: mask, reveal for the role allowed to reveal, and audit. The user's ruling on D-09 ([account-service.md](account-service.md#access-admin-reads-user-writes-user-decision-on-d-09)) names one role that reveals, `ADMIN`, and one way to reach the data, read-only views from admin option 7. The transaction card number follows the same rule. The user's ruling decides it, so no new user question is needed:

- `listTransactions` and `viewTransaction` accept `USER` and `ADMIN`. The list carries no card number.
- `validateTransaction`, `addTransaction`, `latestTransaction` and `requestTransactionReport` stay `USER` only. An `ADMIN` token gets `403 ACCESS_DENIED`. The report status and download keep the approved rule: a `USER` sees their own runs, and an `ADMIN` sees all runs.
- A new endpoint, `POST /api/transactions/{tranId}/unmask` `{fields: ["cardNum"]}`, is `ADMIN` only (`operationId` `unmaskTransaction`). It returns the clear card number with `Cache-Control: no-store`. It writes one `ops.audit` row (`action = 'UNMASK'`, subject type `TRANSACTION`, subject key the `tran_id`, field `cardNum`) in the same transaction. A `USER` token gets `403 ACCESS_DENIED`. A failed audit insert gives `500 UNMASK_AUDIT_FAILED`, as in account-service. The unmask reads the master only (`in_master = 1`), as the view does.
- Admin option 7 (`/admin/lookup`) also links to the transaction list and to the transaction view's ID prompt. For an `ADMIN`, those pages are read-only. The list shows only the View action, and the view has a Show control on the card number. A `USER` sees no Show control.
- Only a reveal writes an audit row for a read. A masked view writes none.
- The DEV-C1 target text in `deviations.toml` changes as requested in account-service.md section 7. That covers DEF-TRNV-004.
- The ownership half of DEF-TRNV-004 and Q-TRNV-001 (TRNV question 4): C1 applies (D-SEC-01). A `USER` may view any transaction, as today. The ledger notes of both items cite DEV-C1 for that half, and the decision catalog is not changed.

- **Invalid keys.** With the 3270 shortcuts on, every key except Enter and the keys the screen names shows `Invalid key pressed. Please see below...`. That applies to TRNL, TRNV, TRNA (VAL-TRNA-013) and RPTS. VAL-RPTS-006 is must-preserve, so RPTS keeps it, with the cursor on Monthly. ## 9. Partial deviations: what stays tested

Ruled 2026-11-10, after the ledger review of section 6. A deviation entry exempts the whole item from the test gate. Several items in section 6 change only part of what they describe, and the rest of each item is still required. So no ruling here exempts a retained part from tests. This needs no new user decision: only the architecture part of each item changes.

**Rule.** For every architecture-dependent or security entry, the ruling states one of two things.

- **Whole item.** Nothing observable is left, or every retained outcome is carried by another item that stays required. That item is named, and the deviation stays as it is.
- **Partial.** The item keeps an outcome of its own. The entry then gets two fields:
  - `retained`: the kept parts, as testable statements;
  - `requires_test = true`.

  `verify-ledger` and the trace matrix treat such an item as required in the decided mode, like an item with no entry. The gate fails until a passing test cites it. `retained` is required when `requires_test` is true. The ledger owner adds both fields and their check to `tracelib/ledger.py` and `matrix.py`, with tests.

## 11. Character set of the free-text fields (2026-11-10)

TRNA's `source` (10), `description` (60), `merchantName` (30), `merchantCity` (25) and `merchantZip` (10) have no content rule (VAL-TRNA-006), so they follow the policy in [data-model.md](data-model.md#text-repertoire-and-width), as account update's free-text fields do ([account-service.md](account-service.md#12-character-set-and-column-width-in-account-update-2026-11-10)).

- They accept every character from U+0000 to U+00FF, the 256 characters a legacy byte holds, up to the same lengths. Normalisation is unchanged: as the contract says, these fields are stored as typed, and only the trailing pad is dropped by the column rule. `FormRules` is not changed.
- A character above U+00FF gives `400 UNSUPPORTED_CHARACTER`, `<label> contains a character that is not supported.`, field = that field, checked after `required` and before `maxLength` in rows 6 to 15. The longest text, with `Merchant Name` or `Merchant City`, is 57 characters, within TRNA's 78.
- The columns become Unicode in data's `V411` (confirmed): `source`, `description`, `merchant_name`, `merchant_city` and `merchant_zip` on `core.daily_tran` and `core.transaction`, and `raw_record` (`NCHAR(350)` BIN2) on `core.daily_tran` and `core.daily_reject`. The service builds `raw_record` with the strict ISO-8859-1 encoder of `platform/legacy-format`, which can always encode these values.
- Tests: a 60-character description of `É`, and a merchant name holding U+00A0 and U+0085, are added and read back unchanged in TRNV and in the posted transaction; `raw_record` holds U+00C9 for each `É`, written as byte `0xC9` in the rejects file; `中` in any of the five fields gets the new text with that field and writes nothing.

## 12. Contract v6 (2026-11-10)

**Question 13, decided under the user's standing delegation.** An exhausted ID range in TRNA gives `500 ADD_FAILED`, `Unable to Add Transaction...`, field `acctId`, with nothing written: the legacy write-failure text, and no new code. The service logs one `ERROR` line with event `TRAN_ID_EXHAUSTED`, the mode and the correlation ID, with no ID value, and S37 asserts that line. ## 15. Report request defaults in the build (2026-11-11)

The backend's first RPTS build (`cf24af6`) chose four behaviours where contract v8 says nothing. They are ruled here against that source, the Airflow report-account test in `modernization/airflow/tests/` and the infra README. The backend writes them into contract v9.

1. **`INVALID_RUN_ID`: approved.** `400`, no `field`, text `Report run ID must be a positive number...`. A `runId` is valid when it is 1 to 19 digits and its value is from 1 to the `BIGINT` maximum. Leading zeros are allowed (`007` is run 7). Anything else gets this problem: `0`, a sign, a non-digit, 20 or more digits, or a value above the maximum. No run can have such an ID, so a `404` would add nothing.
2. **Trigger retries: approved, with one correction.** These are retried: a connection error, a timeout, a `5xx` from either call, and a `2xx` sign-on answer with no usable `access_token`. Retrying is safe because `dag_run_id` `tranrept-<runId>` is the same on every attempt, and Airflow answers `409` for a run that already exists. A `401` on the run call renews the token once in the same attempt. After that, any other `4xx` from the run call, or any `4xx` from the sign-on, is a definite failure. This includes `401` after the renewal, `403`, `404` (DAG missing), `422` and `429`. Redirects are not followed, so a `3xx` is also definite. The defaults `retries 3`, `backoff 1s` (doubling) and a `timeout` of `10s` for connect and for each response are approved. **Correction:** those values let one `POST` hold its request thread for about 87 s, or more when a token is renewed. A new setting, `carddemo.transaction.report.trigger.deadline` (default `30s`), bounds the whole trigger. No attempt starts after the deadline, and each call's timeout is the smaller of `timeout` and the time left. Reaching the deadline counts as "retries used up", which is step 7. **Settings are checked at start (ruled 2026-11-11).** `deadline` and `timeout` must be positive, `backoff` zero or positive, and `retries` zero or more. Any other value fails the service's start with the property's name; it is never clamped or replaced by a default. A `timeout` longer than `deadline` is allowed, because the time left caps each call anyway. **The deadline does not change what an outcome means.** A call that the deadline cuts off has an unknown outcome, the same as a timeout: Airflow may have created the run. Every attempt, the last one included, sends the same `dag_run_id`, so `409` still counts as started. A `2xx` or `409` that arrives within the deadline is a success even after earlier unknown outcomes. Only when the deadline passes with no such answer does the service run step 7. Test: a stub that never answers, with a deadline of 2 s, gets `503 REPORT_TRIGGER_FAILED` within the deadline plus 1 s, and the row is `FAILED`/`TRIGGER_FAILED`. A definite failure after an attempt whose outcome was unknown may leave a DAG run in Airflow. That run does nothing, because the launch refuses a `TRIGGER_FAILED` row and the first step's compare-and-set needs `REQUESTED` ([data-model.md](data-model.md#report-runs-batchreport_run)).
3. **Airflow sign-on: approved.** It follows the tested helper, not a guessed endpoint. The service sends `POST <CARDDEMO_AIRFLOW_URL>/auth/token` with a JSON body `{"username", "password"}` and reads `access_token`. The Airflow test proves the endpoint in four checks: the sign-on returns `201` with `access_token`, a wrong password gets `401`, the first run call gets `200` and a second call with the same run ID gets `409`. If the infra helper or the Airflow version changes the endpoint, the stub and this call change together.

1. **The hash is in the run row.** `batch.report_run.output_sha256 BINARY(32)` (V424, [data-model.md](data-model.md#report-runs-batchreport_run)) is set by the `UPDATE` that writes `COMPLETED`, in both completion forms of contract 4.3 and 4.8, to the intent's sha256 that the publication verified. A report run has exactly four statuses (`REQUESTED`, `RUNNING`, `COMPLETED`, `FAILED`; no `SUPERSEDED`), and only `COMPLETED` carries a hash. A `COMPLETED` row is never changed: the failure listener and recovery change only `RUNNING` rows, and the I4 restart writes nothing. `transaction_svc` gets `SELECT` on that one column and nothing on the job execution context.
2. **One query binds the row, the root and the hash.** The existing download query (contract 4.10, "Who resolves when") returns `output_sha256` too. The `runId` is bound and checked as now (step 1, `INVALID_RUN_ID`; step 2, the owner rule). No second query reads the hash.
3. **Order. Every step before 3.7 ends before any header or byte of the body is sent.**
   1. Not `COMPLETED`: `409 REPORT_NOT_READY`, as now.
   2. `COMPLETED` with no `output_sha256` (completed before V424): `500 REPORT_FILE_MISSING`, log reason `NO_SHA256`.
   3. `resolve` and `existingFile(root, "reports", "tranrept", "<runId>", "TRANREPT.txt")`, unchanged (marker, no link, owner, `0600`). A failure gives the existing answer and reason. These checks stay as defence in depth. The guarantee comes from 3.6.
   4. **The source is opened once:** `Files.newByteChannel(file, READ, NOFOLLOW_LINKS)`. That path is never opened again.
   5. **A private snapshot.** The staging folder is the setting `carddemo.transaction.report.staging-dir`, an absolute path equal to its normalised form (`Path.normalize()`), whose last name follows the output-root module's segment rule. The normalised form is required so that a `..` after a symbolic link cannot name one folder when the path is compared and another on disk (confirmed by the security sign-off of output-root v9 section 9, with these refinements). At start the value is parsed once, with `Path.of(value)`, and every later use takes that `Path`, never the raw string again. The start fails, with a message that names the property and never its value or a path, when: the value is empty or relative; `Path.of` throws `InvalidPathException` (a NUL, for example; its message holds the input, so it is never logged or passed on); the value has no parent or no last name (`/`); it differs from its `normalize()`, which means it holds a `.` or `..` element (`Path.of` already collapses `//` and drops a trailing `/`, so `/a//s` and `/a/s/` are accepted as `/a/s`); the last name breaks the segment rule (`/a/s/.` and `/a/s/..` fail here); or `toRealPath()` of the parent fails (missing, `EACCES`, `ELOOP`; the `IOException`'s message holds the path and is never logged or passed on). Its default is `<CARDDEMO_VAR_DIR>/private/transaction-service/`, on the local disk in development. It must be on a local POSIX file system (APFS on macOS, ext4 or xfs on Linux, as the tests run): not NFS, not a FUSE mount and not object storage. A deployment that maps `var/` to object storage or a network file system (D-NFR-09) sets it to a local path; no volume is provisioned for it here. **Levels and checks (revision 4, D1 to D3).** With the default, the base is `CARDDEMO_VAR_DIR` as `varDir` resolved it, and the levels are `private/` and then `transaction-service/`. With an override, the base is the configured folder's parent, which must exist, and the only level is the configured folder itself; nothing above it is created or checked. At start, transaction-service resolves the base with `toRealPath()`; a missing parent, or one that is not a directory, fails the start with the property's name. It also fails the start, with the property's name, when the staging folder (the resolved base joined with the folder's name) is `<CARDDEMO_VAR_DIR>/out/`, is inside it, or contains it; when `out/` exists, the comparison is also made with its real path (C3). The base passed to `privateDirectory` is always the canonical one resolved once at start, `varDir` as returned or the override parent's `toRealPath()`, and is never derived again from the raw value at a download (C4). The comparison is on resolved paths, so an alias or a link above the folder cannot hide it, and a link at the folder itself is refused by the level check below. So no output root, intent clean-up, retention, rotation or db-migrate listing ever sees a snapshot, with the default or with an override, and no output is ever written there. An override names a folder used only for these snapshots, because the start clean-up (item 4) deletes its own names there. At each download one new public method of `platform/output-root` creates and checks the levels: `OutputRoot.privateDirectory(Path base, String... segments)` ([contract 4.10.2](batch-execution-contract.md#4102-shared-interface-platformoutput-root)). The base must be an absolute, existing directory; its owner and mode are not checked. Each missing level is created with `createDirectory` and mode `0700` given at creation, and a concurrent creation is accepted. Each level, new or existing, must pass the path checks of contract 4.10 (a POSIX file system, a directory, not a symbolic link, owned by the service user, no group or other bit), through the module's own private check, not a copy. The existing public methods (`ensure`, `ensureDirectory`, `existingFile`, `resolve`) and the checks of `CARDDEMO_VAR_DIR` keep their behaviour. In particular `CARDDEMO_VAR_DIR` gains no requirement: `ensure` creates it with the umask's mode, and nothing guarantees `0700`. transaction-service never creates `CARDDEMO_VAR_DIR`. A failure is never repaired, the download gets `500 REPORT_FILE_MISSING`, and the service's start is not affected (O6). The reason is: `OUTPUT_PERMISSIONS` for a failed check; `OUTPUT_ROOT_INVALID` for a base that is missing or not a directory, as `resolve` already refuses a missing `CARDDEMO_VAR_DIR` for the source; `SNAPSHOT_IO` for an I/O error while a level is created or read (`EACCES`, `ENOSPC`, a read-only file system). The log line has the run ID and the reason code only; the module's exception messages hold paths and are never logged. The snapshot is one channel: `FileChannel.open(<folder>/download-<random UUID>.tmp, CREATE_NEW, READ, WRITE, DELETE_ON_CLOSE, NOFOLLOW_LINKS)`, with mode `0600` given at creation. On Linux and macOS the JDK removes the name right after the open while the channel stays open. The JDK documents `DELETE_ON_CLOSE` as best effort, so the service does not rely on it: right after the open it checks that the name is gone (`Files.exists(name, NOFOLLOW_LINKS)`), and if the name is still there it deletes it. If that delete fails, the download is refused. From then on the snapshot has no name in the file system. It can be reached only through this channel.
   6. **Copy, read back, hash.** The service copies the source channel into the snapshot channel through one fixed buffer (64 KiB) and closes the source. It does not force the snapshot: the snapshot has no name and does not outlive the process, so no durability is claimed or needed. Then it sets the snapshot channel to position 0 and hashes and counts everything read back through that channel. Then it compares the digest with `output_sha256` (`MessageDigest.isEqual`). If they differ: `500 REPORT_FILE_MISSING`, reason `PUBLICATION_MISMATCH`. What is checked is the snapshot itself, so a source changed during the copy is refused too.
   7. **Serve the same channel, synchronously.** The controller writes to the `HttpServletResponse` on the request thread. It returns no `StreamingResponseBody`, `DeferredResult` or other async body: an async body closes its channel only if its writer runs, so an async timeout or a refused executor task would leak the channel and its disk space, and the async timeout would cut off a large download. Only after 3.6 succeeds does the service set status `200` and the existing headers, with `Content-Length` set to the byte count of 3.6. Then it sets the same channel to position 0 again and streams it through a fixed buffer. There is no `FileSystemResource`, no `InputStreamResource` over a path, and no second open. No other header is added.
   8. **Clean-up.** The source and the snapshot channels are each opened in a try-with-resources block that covers 3.4 to 3.7, so both are closed on every end: completion, a refusal, an I/O error, a client that aborts (an `IOException` from the response write), and a request that times out or is cancelled. Closing the snapshot channel frees its space. **Before the commit (revision 4, L1):** an error after the status and headers are set and before the response is committed resets the response (`response.reset()`, which drops the status, `Content-Length` and `Content-Disposition`) before the refusal is written, so a problem body never goes out under the report's headers. Once the response is committed, an error in the middle of the body aborts the connection, and no `500` is attempted; the body is shorter than `Content-Length`, so the client sees the truncation. **Body errors stay in the download (L2):** the download catches every `IOException` of the body phase itself, a client abort included. It closes the channels, logs the run ID and the reason `BODY_IO` at `WARN`, and does not rethrow. When the response is not yet committed, it resets it and writes the refusal first; a write that fails again is logged as `BODY_IO` and dropped. So the exception never reaches `ProblemExceptionHandler`, whose catch-all would log `unexpected error` at `ERROR` and try to write a `500`.

   Every refusal logs the run ID and the reason only, never content or a hash. It changes nothing: the file and the row stay as they are, and nothing infers, backfills or repairs a hash. The user recovers with a new request, which makes a new run. An I/O failure while copying, reading back or creating the snapshot, a full disk included, gives the same `500 REPORT_FILE_MISSING`, reason `SNAPSHOT_IO`. The status read does not change: `downloadable` is still true for every `COMPLETED` row.
4. **Leftovers after a crash.** A name can be left only when the process dies between the snapshot's open and the removal of its name, or when the fallback delete of 3.5 did not run. At start, after `varDir`, transaction-service lists the staging folder as configured (`carddemo.transaction.report.staging-dir`, resolved as in 3.5; the default folder only when no override is set), once and without following links (revision 4, D2). When the folder does not exist, nothing is done; if a level disappears between that check and the `privateDirectory` call, the call may create it again (`0700`, empty), which is harmless (C2). Otherwise it first passes every level through `privateDirectory`, which creates nothing because every level exists. When a level fails its check, or the listing fails, nothing is deleted: the start logs the reason code and goes on (O6). Where the listing is a `SecureDirectoryStream` (Linux), the attributes are read and the deletes made relative to that stream, so a swap of the folder after its check cannot redirect them (C2). Otherwise it deletes only the entries that are regular files owned by the service user and are named exactly `download-<36-character lower-case UUID>.tmp`. Each other entry stays where it is and is never repaired. The listing stops after 10,000 entries and leaves the rest. A failed delete is counted and never fails the start. The log carries counts (deleted, kept, failed, whether the listing stopped) and reason codes only, never an entry name or a path, because an entry can have any name (contract 4.8, Logs). The clean-up never touches `out/`, the pre-instance outputs, or any other folder. A second process that removes a live process's name does no harm: that snapshot is already nameless, or it is still open through its channel.
5. **Bounds and limits, as they are.** Memory per download is the fixed buffers only, whatever the report's size. No size limit applies, so every valid report can be downloaded, and no free-space threshold is set, because it would refuse a valid report while space remains. Disk use is one full copy of the report per download in progress, on the staging folder's file system, freed when its channel closes or the process ends; N downloads of a report of S bytes use N × S at once, and nothing bounds N or how long each one lasts: a client that keeps reading within the connector's write timeout holds its request thread and its S bytes for as long as it reads. No concurrency bound is chosen. With the default folder that is the file system of `out/` and the batch outputs, so many concurrent downloads of a large report can use up the space that a batch job needs. This design does not claim otherwise; an operator who needs the separation sets the staging folder to another local file system. A full disk fails safely on both sides. The download is refused with `SNAPSHOT_IO` (3.8) before any header is sent, and never reports a field or format error. A batch job whose write fails for lack of space fails its step before it commits an intent (every working file is closed, forced and hashed before the intent), so the publication never starts. The no-replace publication never treats a final folder without its manifest as complete (contract 4.8), so a full disk cannot make a partial output readable. Nothing repairs a source or an output. On a file system that is not local POSIX the design fails safely but is not supported: a name that cannot be removed refuses the download (3.5), a seek that fails gives `SNAPSHOT_IO`, and names that such a file system keeps for open unlinked files (`.nfsXXXX`, `.fuse_hidden*`) are left alone by the start clean-up, which deletes only its own exact names.
6. **What it guarantees.** The bytes sent are the bytes of the snapshot, read through the same channel that was hashed, and they match the committed hash. A source swapped before the open is refused by the hash, whatever passed the path checks. A source swapped after the open is not read. A source changed in place before or during the copy is refused, a torn mix included. A source changed after the copy cannot reach the response. After 3.5 no other process can open the snapshot by name. The snapshot holds what the report holds: account IDs and amounts, and no card number (the report's detail line has none). A `fileKey` or `stat` comparison is not added, because it would suggest a guarantee it cannot give.
7. **What it does not guarantee, stated in the contract as residuals.**
   - It detects a change only when someone downloads. It does not prove that the file stays intact between downloads.
   - It is not a signature. Whoever can write `batch.report_run` and the file (`batch_svc`, the database owner) can change both.
   - It gives no confidentiality, and it cannot see a fault inside the producer before the producer hashes.
   - A process of the same OS user that opens the service's open descriptors (`/proc/<pid>/fd` on Linux) or attaches a debugger can change the snapshot. Such a process could also change the JVM's memory, so no reader in the process can rule this out.
   - Two downloads that run while the file changes can end differently, one served with the committed bytes and one refused. Both outcomes are correct.
   - The fallback delete of 3.5 deletes by name (revision 4, L3). After the JDK has already removed the name, a process of the same OS user can create a new file at that name before the check, and the fallback then deletes that file. The JDK's own unlink has the same race. In a `0700` folder only the service user can do this, so it is part of the same-user residual above.
   - **A-1, inheritable ACLs** ([contract 4.10](batch-execution-contract.md#instance-and-root), path checks). The level check sees only the owner and the mode bits. On macOS, an inheritable access-control entry on `CARDDEMO_VAR_DIR`, on the staging base or on an ancestor gives another principal access to the `0700` levels and to a `0600` snapshot, in the window between its open and the removal of its name or through a hard link made in that window. There, "cannot change or read what is served" (below) does not hold. The same applies to the report itself under `out/`. The residual is mainly macOS: under Linux acl(5), the `0700` and `0600` create modes set the mask, so an inherited named entry gets no effective rights, and a mask that grants anything shows in the group bits, which the level check refuses. That Linux reasoning comes from acl(5) and has not been verified on a Linux host. The JDK has no ACL view on macOS or Linux (`AclFileAttributeView` is Windows-only), so the module cannot see such an entry, and it is a stated precondition, as backend's output-root contract (document v10, section 3) states it: `CARDDEMO_VAR_DIR`, the staging base and their ancestors carry no inheritable entry for another principal, and infra's operator check in `make setup` and `make up` refuses to start when the setting or the base carries one.
   - An ancestor of the staging folder that another user can write lets that user swap the folder or one of its levels (revision 4, D2). That denies downloads (a failed check, or `SNAPSHOT_IO`), but cannot change or read what is served: the bytes come from the snapshot channel, hashed after its read-back (item 6), and a snapshot created in a swapped folder is still `0600`, owned by the service and reached only through its channel.
8. **Tests** (backend, with the code).
   - **File system, on each OS the build runs on (Linux in CI, macOS locally).** Right after the snapshot's open, the staging name does not exist. While a download is paused after 3.6, the staging folder has no entry. After completion, after a client abort in the middle of the body, after a timeout and after a refusal, the channel is closed (the process's open-descriptor count is back to where it was) and the folder is empty. A test with `DELETE_ON_CLOSE` made ineffective (a seam that skips it) shows that the fallback delete removes the name.
   - **Reader, temp folder, no database.** A match serves the exact bytes. One byte changed in place, and another `0600` file renamed into place, each give `REPORT_FILE_MISSING` with no body. A source changed during the copy is refused. `NO_SHA256` is refused. A staging folder that is a symbolic link, or that has a group bit, is refused with `OUTPUT_PERMISSIONS`. A failing snapshot write (a seam) gives `SNAPSHOT_IO`. A link at the source is refused by the existing check. The log holds neither content nor a hash.
   - **Size.** A report larger than the test JVM's heap (for example 256 MiB under `-Xmx64m`) is served whole and matches.
   - **Synchronous serving and ends.** The controller's return type is not an async body type. A client that closes its socket in the middle of the body leaves both channels closed, the folder empty and the descriptor count unchanged. A full disk through a seam gives `SNAPSHOT_IO` with nothing sent. `Content-Length` equals the bytes hashed. No `force` call is made (a seam counts it). A child JVM paused at a seam between the snapshot's open and the removal of its name gets `SIGKILL`, and the next start removes the name. A relative `staging-dir` fails the start with the property's name.
   - **Race.** One thread rewrites the source in place and swaps it by rename in a loop while the download runs many times. Every `200` body hashes to the committed value. Every other answer is `REPORT_FILE_MISSING`.
   - **Start clean-up.** A leftover `download-<uuid>.tmp` is removed. A file with another name, a symbolic link with a matching name and a folder are kept and counted. A staging folder that is a file is logged with its reason code, and the start still succeeds.
   - **Output-root helper (`OutputRootFilesTest`, revision 4).** `privateDirectory` with a `0755` base creates `0700` levels and returns the folder. An existing level with a group bit, a level that is a symbolic link (its target unchanged) and a level that is a file each give `OUTPUT_PERMISSIONS` and change nothing. A missing base gives `OUTPUT_ROOT_INVALID`. A base that refuses the creation (mode `0500`) gives an I/O error, which the download maps to `SNAPSHOT_IO`. A level created concurrently is accepted after its check. `..`, an empty segment and a segment with `/` are refused. The existing `ensureDirectory` tests are unchanged and pass.
   - **Staging setting (revision 4, sign-off T2).** Refused at start, each with a message and logs that hold the property's name and never the value (a sentinel in the value): `/a/./s`, `/a/../s`, `/a/b/../s`, a `..` after a symbolic link, `/a/s/.` and `/a/s/..` (segment rule), `/`, a value with a NUL, and a parent that cannot be resolved (`ELOOP`). Accepted as `/a/s`: `/a//s` and `/a/s/`. An override whose parent is missing fails the start with the property's name. An override equal to `<CARDDEMO_VAR_DIR>/out`, inside it, inside it through a symbolic link or an alias above it, or containing it (`CARDDEMO_VAR_DIR` itself) fails the start with the property's name. With an override, the start clean-up lists the overridden folder and never the default one: with a leftover planted in each, only the override's is removed. A staging folder with a group bit, or that is a symbolic link, at start: a leftover planted in it stays, the reason code is logged and the start succeeds. No clean-up log line holds a planted sentinel name or the folder's path.
   - **Sign-off T1, T3, T4.** A `0777` base (and `1777` where possible) is accepted by `privateDirectory` and keeps its mode. A staging folder whose second level is missing, with a file of the matching name beside it: the start clean-up deletes nothing and logs no path. A base removed after the start: the download gets `OUTPUT_ROOT_INVALID` with no header and no body, and the log holds the run ID and the code only.
   - **Errors around the commit (L1, L2).** A seam that fails the first read-back read after the headers are set gives a problem response with neither `Content-Length` nor `Content-Disposition`. A client abort in the middle of the body logs `BODY_IO` with the run ID, no `ERROR` line `unexpected error` is logged, and `ProblemExceptionHandler` is not invoked.
   - **Interface (L4).** `OpenApiExportTest` stays byte-identical after the controller changes to writing to `HttpServletResponse`, and `ReportService.download`'s Javadoc says that the report holds no card numbers.
   - **Database slot.** The one query returns the column. The grants test and `EffectiveGrants` show `output_sha256` readable by `transaction_svc` and the job execution context refused. The CHECKs refuse `COMPLETED` without a hash and a hash on a non-`COMPLETED` row. SQL Server checks them on an `UPDATE` only when the statement sets `status` or `output_sha256`. On a row completed before V424, which has `NULL`, an update that sets `status` is refused and leaves the row unchanged, and an update that sets only `finished_at` succeeds and leaves the row `COMPLETED` with `NULL`.
   - **Producer (batch-service).** Both completion forms set the column to the intent's sha256. The I4 restart compares the file with the context's value and with the column, and either difference is `PUBLICATION_MISMATCH`.
9. **Scope.** This is not part of N1. The frozen N1 pilot is unchanged, and its acceptance stays partial: it claims no report download.
