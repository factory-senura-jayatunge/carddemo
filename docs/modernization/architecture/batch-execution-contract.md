## Transport

- Base URL `http://127.0.0.1:<batch-service port>`. `/internal/*` listens on loopback only.
- Every request sends `Authorization: Bearer <CARDDEMO_BATCH_INTERNAL_TOKEN>`, compared in constant time and never logged. A missing or wrong token gets `401 UNAUTHENTICATED` (not retryable).
- Bodies are `application/json`. Errors are `application/problem+json` in the platform `ApiProblem` shape (`type`, `title`, `status`, `code`, `message`, `field`, `severity`), plus the members listed per code. `field` names the offending request member on a `400` and is null otherwise.
- No request carries a file path. No body carries record values or exception text. **No caller-supplied value (`runKey`, `windowRunKey`) is ever used in a file or folder name.** Output folders are named by IDs that batch-service generates (section 2.3).

## 1. Cycles: `POST /internal/cycles`

Request: `{"businessDate": "2022-07-06", "interest": "always" | "month_end" | "never"}`.

batch-service resolves the policy into a stored yes or no (`month_end` means `businessDate` is the last day of its month) and stores `batch.cycle.interest_parm` (`yyyyMMdd00` when due, NULL when not).

Cycle body (every success and every cycle `409`):

```json
{"cycleId": 7, "businessDate": "2022-07-06", "attempt": 1, "interest": true, "interestParm": "2022070600",
 "status": "OPEN", "openedAt": "2022-07-06T21:00:00.000Z", "closedAt": null}
```

- `interest` is the stored boolean; the DAG's `interest_due` branch reads it and nothing else.
- `attempt` is `batch.cycle.attempt`: 1, raised by each `cycle-rerun` (section 7).
- `status` is `OPEN` from registration until the DAG's completing window close, then `COMPLETED`.

| Response | When | Retry |
| :-- | :-- | :-- |
| `201` + cycle | New cycle, `OPEN`. | Safe to repeat. |
| `200` + cycle | The cycle exists, is `OPEN`, and the resolved `interest` is equal. The DAG resumes it: completed jobs answer `JOB_INSTANCE_COMPLETE`, failed ones restart. | Safe to repeat. |
| `409 CYCLE_COMPLETED` + cycle | The cycle is `COMPLETED`. The DAG fails here, before it opens the window, so a re-triggered run for a finished date never blocks online writes. | No. |
| `409 CYCLE_PARAMETERS_DIFFER` + cycle | The resolved `interest` differs from the stored one. | No. |
| `400 INVALID_REQUEST` | Missing or unparsable `businessDate`, unknown `interest`. | No. |

A V4xx migration narrows the `batch.cycle.status` check to `OPEN` and `COMPLETED`.

## 2. Launch: `POST /internal/jobs/{jobName}/executions`

Request: `{"params": {...}}`. batch-service builds the job parameters. Airflow never sends `run.id`, and no job uses an incrementer on this path.

### 2.1 Identity and parameters

| Kind | Jobs | Identifying parameters | Non-identifying parameters |
| :-- | :-- | :-- | :-- |
| cycle | `archiveMasterJob`, `ingestDailyFileJob`, `postDailyTransactionsJob`, `calculateInterestJob`, `statementJob`, `applyRetentionJob`, `purgePendingAuthorizationsJob` | `cycleId` (request), `businessDate` and `attempt` (from `batch.cycle`) | `interestParm` (from the cycle, `calculateInterestJob`); `expiryDays` and `commitInterval` (from configuration, the purge); `expiryDays` (the same setting, `postDailyTransactionsJob`, for D-33 matching). A request `businessDate`, if sent, must equal the cycle's. |
| report | `transactionReportJob` | `runId` (an existing `batch.report_run` row) | none: the job uses the row's stored parameters, not the request's |
| run-keyed | `categoryBalanceListingJob`, `dataLoadJob`, `disclosureGroupReloadJob`, `transactionTypeMaintenanceJob`, `exportMastersJob`, `importMigrationJob` | `runKey` = `"<dag_id>/<run_id>/<task_id>"` from the Airflow context, 1 to 250 characters | `businessDate` (required: the DAG's logical date or `conf` override; the timestamps the job writes take their date from it); `windowRunKey` (required for the jobs that need a window, section 6); `migrationName` (required, `importMigrationJob`: the folder under `<CARDDEMO_VAR_DIR>/inbound/migration/`, [batch.md](batch.md#export-and-import-ruled-2026-11-11)) |

- `make load` launches `dataLoadJob` directly with `runKey = "cli/<host>/<UTC timestamp to the microsecond>/<random UUID>"` and opens and closes its own window around the launch (section 6).
- Non-identifying parameters are fixed at the first launch of an instance and stored with it. A restart uses the stored values. A restart request with a different value gets `400 INVALID_JOB_PARAMETERS` with `field`.
- `categoryBalanceListingJob` is run-keyed: it is read-only and has no `batch.report_run` row. If a screen ever triggers it, it gets a report-runs endpoint like the transaction report, through this document.
- **The cycle row under the launch lock (ruled 2026-11-11, in force; review of `3de94476`, C1).** `prepare` reads the cycle (status, `attempt`, business date, `interest`) before the launch takes any lock, so its `attempt` can be stale: a launch prepared while the cycle is `COMPLETED` at attempt n can wait on the launch lock while `cycle-rerun`'s restore, which holds that lock exclusively, commits `OPEN` at attempt n+1, and would then create an instance of attempt n, a lower attempt that nothing may reach again, inside the rerun's window and after the rerun's check for live executions. So for every cycle job other than `purgePendingAuthorizationsJob`, the launch reads the cycle row again while it holds the shared launch lock, only on the paths that would create a job instance or an execution: after the answers that create nothing (`409 JOB_INSTANCE_COMPLETE` for a completed instance, and `409 JOB_EXECUTION_RUNNING` for a live execution that is not recoverable, section 2.2) and before it recovers a lease (section 4.4), checks the window (section 6), starts or restarts. There it refuses:
  - a cycle whose status is `COMPLETED`: `409 CYCLE_COMPLETED` with the cycle body, not retryable. The window already refuses such a launch (section 6), except inside a `cycle-rerun`'s own window before its restore commits;
  - a cycle whose `attempt` differs from the prepared `attempt`: `409 CYCLE_ATTEMPT_CHANGED` with the cycle body. A new request prepares its parameters again, so the code is retryable for a caller; `SpringBatchJobOperator` fails the task without a retry (section 5), because that task was planned for the replaced attempt and the next DAG run launches the new attempt in the DAG's order.

  Both refusals create no job instance and no execution, for a first start, for a restart of a `FAILED` or `STOPPED` instance, and for a recoverable execution, which is not recovered, alike. Because the answers that create nothing come first, clearing a completed task still gets `JOB_INSTANCE_COMPLETE` and succeeds (section 5), also after its cycle is `COMPLETED` and after a rerun raised the attempt (amended 2026-11-11 on the review's K1). The serialization against `cycle-rerun` comes from the launch lock, which the restore takes exclusively, not from a row hint: the read takes no `UPDLOCK` or `HOLDLOCK`, because the launch's decision runs in no transaction that spans the read and the creation of the execution. The check runs under the shared launch lock for each of these jobs, whether or not the job needs a window; today every cycle job other than the purge needs one (section 6), so a later cycle job that needs none still takes the lock for this check. Rerun Part 1 relies on the attempt refusal: posting and interest do not check the attempt themselves.

  Tests (C1, against SQL Server): A launch of a cycle job other than the purge, for a `COMPLETED` cycle inside a `cycle-rerun`'s window before its restore, gets `409 CYCLE_COMPLETED` and creates no instance; the purge's launch is not refused. A launch of `postDailyTransactionsJob` prepared against the `COMPLETED` cycle at attempt n is held on the launch lock (a test seam) while the rerun's restore commits attempt n+1; it then gets `409 CYCLE_ATTEMPT_CHANGED`, and no instance of attempt n is created: once as a first start (no attempt-n instance before) and once as a restart (a `FAILED` attempt-n instance, which gets no new execution). The same request sent again starts an attempt-n+1 instance. The operator fails the task without a retry on either code. Clearing keeps working (K1): a cleared, completed `postDailyTransactionsJob` task launched after its cycle's completing close, and a cleared, completed task of the replaced attempt's DAG run after the rerun, each get `409 JOB_INSTANCE_COMPLETE` and the operator succeeds, with no new execution; a live, not recoverable execution of attempt n still gets `409 JOB_EXECUTION_RUNNING`; a recoverable one of attempt n after the rerun gets `409 CYCLE_ATTEMPT_CHANGED` and is not recovered or restarted by that launch.
- `transactionReportJob` refuses a `runId` whose row failed with `TRIGGER_FAILED` (`400`, `field: runId`). Its status writes on the row are compare-and-set, and recovery marks the row `FAILED` (`OWNER_LOST`) in the revoke transaction ([data-model.md](data-model.md#report-runs-batchreport_run)).

### 2.2 Answers

Every job-instance answer, `202` or `409`, has the same members:

```json
{"executionId": 123, "jobName": "postDailyTransactionsJob", "executionStatus": "STARTED",
 "exitStatus": "EXECUTING", "rejectCount": 0, "restart": false}
```

`executionStatus` is the Spring Batch `BatchStatus`. `exitStatus` is `COMPLETED`, `COMPLETED_WITH_REJECTS` or `FAILED` once terminal, otherwise `EXECUTING` or `UNKNOWN`. `rejectCount` is an integer. `restart` is on `202` only.

| Response | When | `executionId` |
| :-- | :-- | :-- |
| `202` | A first run, or a restart (`restart: true`) of an instance whose last execution is `FAILED` or `STOPPED` and whose job allows restart. This includes an execution that the launch has just recovered (section 4.4). | the new execution |
| `409 JOB_EXECUTION_RUNNING` | The last execution is `STARTING`, `STARTED` or `STOPPING`, and it is not recoverable (section 4.1). | the running execution |
| `409 JOB_INSTANCE_COMPLETE` | The last execution is `COMPLETED`. | the completed execution |
| `409 JOB_INSTANCE_NOT_RESTARTABLE` | The last execution is `ABANDONED`, or `FAILED`/`STOPPED` and the job does not allow restart. | the last execution |
| `409 BATCH_WINDOW_REQUIRED` | The job needs a window (section 6) and no window is open for exactly this `cycleId` or `windowRunKey`. This is a DAG wiring error, not a transient state. | none |
| `400 INVALID_JOB_PARAMETERS` | A missing or malformed param, an unknown `cycleId` or `runId`, a missing `migrationName` folder, a `businessDate` that does not match, a changed non-identifying param on restart, or `calculateInterestJob` for a cycle whose stored `interest` is false (`field: cycleId`). | none |
| `503 WINDOW_CLOSE_IN_PROGRESS` | A job that needs a window waited for its holder's close lock longer than the lock wait (section 9). `Retry-After` is the lock wait in seconds. | none |
| `404 JOB_NOT_FOUND` | Unknown `jobName`. | none |

### 2.3 Outputs

Output folders are `<kind>/<id>`, where the ID is generated by batch-service: the `batch.report_run` ID for the transaction report, `cycleId`-`attempt` for statements, and the Spring Batch job instance ID for the listing. `exportMastersJob` creates a `batch.export_run` row with a generated `exportId` (`BIGINT`). The export writes to `exports/<exportId>`, and the poll returns `"outputs": {"exportId": 42}` once the job completes. `statementJob`'s poll returns `"outputs": {"statementRunId": 17}`, the `batch.statement_run` ID, from the job execution context key `carddemo.output.statementRunId` that the run's insert or claim writes ([batch.md](batch.md#build-rulings-statement-and-transaction-report-2026-11-11)). `importMigrationJob` reads the operator's copy of a published export folder, named by `migrationName`, and loads it into empty master tables of its own database; its rejects go to `imports/<jobInstanceId>`. A missing or unpublished folder (no `MANIFEST.json`) gets `400` (`field: migrationName`). Every output is written and published as [section 4.8](#48-output-publication) states.

## 3. Poll: `GET /internal/jobs/executions/{executionId}`

`200`:

```json
{"executionId": 123, "jobName": "postDailyTransactionsJob", "cycleId": 7, "runId": null, "runKey": null,
 "executionStatus": "STARTED", "exitStatus": "EXECUTING", "rejectCount": 0,
 "startTime": "...", "endTime": null,
 "lease": {"state": "LIVE", "renewedAt": "...", "expiresAt": "...", "recoverableAt": "...", "recoverable": false, "dbTime": "..."},
 "outputs": {},
 "steps": [{"name": "post", "status": "STARTED", "readCount": 120, "writeCount": 118, "skipCount": 0}]}
```

- **The poll never recovers and never writes.** It reports the lease as seen by the database clock: `state` is `LIVE`, `EXPIRED` (not renewed for the TTL), `REVOKED` or `NONE`, and `recoverable` is true once the execution can be recovered (section 4.1). All times are database times, so the caller compares nothing with its own clock.
- `404 EXECUTION_NOT_FOUND` for an unknown ID.

## 4. Execution ownership, fencing and recovery

Requirements: an orphaned execution is not polled forever; a live owner's execution is never failed; the old owner is revoked atomically before the execution is failed; expiry is checked in the fence; every mutating path is fenced; an owner that was paused or suspended and resumes after a takeover can change nothing.

### 4.1 Lease

- A V4xx migration adds `batch.execution_lease` (`job_execution_id BIGINT` PK FK to `BATCH_JOB_EXECUTION`, `owner_id UNIQUEIDENTIFIER`, `owner_host VARCHAR(255)`, `owner_pid INT`, `acquired_at`, `renewed_at`, `revoked_at` NULL `DATETIME2(3)`, `revoked_reason VARCHAR(100)` NULL, `recoverable_after_ms INT NOT NULL`). The process that creates or restarts an execution inserts the row in the same transaction. A restart is a new execution with a new row; revoked rows stay as the record of the takeover. `owner_id` is random per process. `recoverable_after_ms` is the inserting owner's TTL + grace, in milliseconds; it never changes after the insert (an `AFTER UPDATE` trigger in V404 refuses a change with error 50040). Data owns every path that inserts a lease row: `LeaseGuardedJobRepository.createJobExecution` for a start or restart, and the revoked row of a lease-less recovery.
- Settings, with defaults: renewal interval 10 s; TTL 60 s; grace 60 s. The TTL must be at least 3 times the interval, and the grace at least the TTL.
- **Expired**, for reporting only: `renewed_at < SYSUTCDATETIME() - TTL`.
- **Recoverable**: `revoked_at IS NULL AND renewed_at < DATEADD(millisecond, -recoverable_after_ms, SYSUTCDATETIME())` (120 s by default). The limit comes from the row, not from the reader's settings, so it is the owner's TTL + grace even when processes run with different settings. The fence, the renewal, the recovery, the poll's `recoverable` and `batch.v_report_run_stalled` all use this one predicate, so they cannot disagree. An owner that resumes after a pause shorter than TTL + grace, and before anyone recovered it, keeps its lease.
- Only the database clock (`SYSUTCDATETIME()`) is compared. Host clocks, the JVM's monotonic clock and Airflow's clock never decide liveness.

### 4.2 Renewal

The owner's scheduler thread runs `UPDATE batch.execution_lease SET renewed_at = SYSUTCDATETIME() WHERE job_execution_id = @id AND owner_id = @me AND NOT <recoverable> AND revoked_at IS NULL`. When it updates 0 rows, the lease is lost for good: the execution is marked lost in memory, the step stops at its next transaction boundary, and the process writes nothing more for it, including Spring Batch status updates (4.5).

### 4.3 Fence

- Every transaction that changes data on behalf of an execution ends with the fence, as its last statements before COMMIT: the renewal UPDATE, then, where section 4.10 requires it, the output-root check. The renewal is therefore not always the literal last statement; nothing but the output-root check runs between it and COMMIT. 0 rows from the renewal: the transaction rolls back and the step fails with `LEASE_LOST`.
- **Order (ruled 2026-11-11).** In an ordinary fenced transaction no lease statement runs before the work: the work's statements come first, then the fence (the renewal, then the output-root check of section 4.10), then COMMIT. Only the publish transaction below renews as its first statement too, and it still runs the fence before COMMIT. No other transaction adds an early renewal.
- The fence's exclusive lock on the lease row is held until the commit, so a revocation cannot fall between fence and commit.
- **Two transaction managers.** Job steps get only the fencing transaction manager: a decorator that registers the fence as a `beforeCommit` synchronization for the execution bound to the thread, and fails a commit with no bound execution. Request handlers (cycle registration, window open and close, report-run reads) use the plain one and hold no lease; window operations are serialized by the window's application lock. A test asserts that every step of every registered job runs through the fencing decorator, and that no job bean can obtain the plain one.
- **Coverage** includes every chunk and every tasklet: `archive`, `claimOnlineAdds`, `stageAuthorizationMatches`, `applyAuthorizationMatches`, `apply_retention`, the `dataLoadJob` steps, `checkDefaultGroup`, the purge, the import, the exports, the report and the listing, the statement capture, render chunks and both publication commits, plus the status writes on `batch.report_run`, `batch.export_run` and `batch.statement_run`.
- **Files.** File operations never happen between the fence and the commit, except in the publish transaction below. Outputs are written and published by [section 4.8](#48-output-publication). The inbound daily file is never moved, rewritten or deleted by a job; each attempt stages from its own immutable archive copy ([section 4.9](#49-inbound-daily-file)).
- **Publish transaction (ruled 2026-11-11).** A job whose intent is in the job execution context (section 4.8) may publish its output inside a fenced transaction, when all of these hold:
  1. The intent `{workPath, sha256}` was committed by an earlier fenced transaction, of this execution or of an earlier one whose context the restart carries. The publish transaction builds nothing and reads no job input.
  2. Its first statement is the renewal UPDATE of section 4.2, which takes the lease row's exclusive lock. With 0 rows the step fails with `LEASE_LOST` before any file operation. The lock is held until the commit, so a recovery cannot revoke the lease between that check and the publication: it reaches its lock timeout and answers `409 JOB_EXECUTION_RUNNING` (section 4.4). The fence before COMMIT still runs. An owner paused while it holds the lock is the case of section 4.5 that the task's `execution_timeout` bounds.
  3. Its file operations are only those of section 4.8 for its own intent: hash the working path, create the target's folder and link the output's files onto the target with no replace, verify the target, and then remove the working path the intent names. Nothing is replaced and no other path is removed. Their time grows with the output's size only, with no wait and no network call.
  4. Every prefix is restart-safe. When the transaction rolls back, or the process dies, after any file operation, the intent stays committed, and the restart publishes as section 4.8 says: an existing target (for a folder, the final folder's `.claim`) is checked against the intent's sha256 (equal: continue; different: `PUBLICATION_MISMATCH`), otherwise the named working path is checked and published. When neither exists, the step fails with `PUBLICATION_MISMATCH`.
  5. The output counts as published only once the commit has recorded it (the step's completion and the output's path in the context). Every later reader, the restart included, checks the target against the committed sha256 again. None relies on the check made before the commit.

  The other form stays allowed: the intent commit, then the publication outside any transaction, then a fenced recording transaction that hashes the target again, as the statement job does. The category balance listing uses the publish transaction.

### 4.4 Recovery (revoke, then fail, in one transaction)

Only a **launch** recovers (section 2), and only an execution that is non-terminal and recoverable. Polls, startup and bulk sweeps never recover. One transaction with `SET LOCK_TIMEOUT 5000`.

**Session settings.** `LOCK_TIMEOUT` and `DEADLOCK_PRIORITY` belong to the session, not the transaction, so on a pooled connection they would reach the next borrower (another job's chunk, a fence). Every code path that sets one (this recovery, the statement capture) restores the defaults, `SET LOCK_TIMEOUT -1` and `SET DEADLOCK_PRIORITY NORMAL`, after a commit and after a failure, **on the same physical connection**. With Spring-managed transactions, a `finally` after `TransactionTemplate.execute` returns runs after the connection is released, so the restore runs either in the callback's own `finally` (before commit or rollback, on the bound connection) or in a `TransactionSynchronization.afterCompletion` while the connection is still bound. If the restore itself fails, the connection is aborted and evicted from the pool, not returned, as the session application lock already does. The test uses a pool of one connection, or compares `@@SPID` before and after, then checks `@@LOCK_TIMEOUT` and `sys.dm_exec_sessions.deadlock_priority`, so it cannot pass on another connection. The recovery transaction:

1. `UPDATE batch.execution_lease SET revoked_at = SYSUTCDATETIME(), revoked_reason = 'OWNER_LOST' WHERE job_execution_id = @id AND <recoverable>`. 0 rows: the owner renewed, or another launch recovered first. Answer from the current state. Lock timeout: the owner is between fence and commit. Answer `409 JOB_EXECUTION_RUNNING`.
2. Mark the job execution and its non-terminal step executions `FAILED`, and its `batch.report_run`, `batch.export_run` or `batch.statement_run` row, if `RUNNING`, `FAILED` with `OWNER_LOST` (a statement run is found by its `job_execution_id`, never by `cycleId` and `attempt`), exit description `OWNER_LOST: lease not renewed since <renewedAt>, owner <host>/<pid>`, `end_time`, `VERSION` incremented. A `PUBLISHING` statement run is left as it is: its intent is committed, and the restart finishes it (section 4.8).
3. Commit, then start the restart, which answers `202 restart: true`.

An execution with **no lease row** is recoverable once its `BATCH_JOB_EXECUTION.LAST_UPDATED` is older than 120 s, a fixed limit: no owner recorded its settings, so the reader's settings are not used. Recovery first inserts a revoked lease row for it with `recoverable_after_ms = 120000`, so the same row lock serializes recoverers. `batch.v_report_run_stalled` uses the same 120 s for a lease-less execution.

### 4.5 A paused owner that resumes

Its next fence or renewal updates 0 rows, so its chunk rolls back and the execution is marked lost. Its Spring Batch repository writes fail the optimistic `VERSION` check, and a repository decorator refuses any write for an execution marked lost. It never overwrites the recovered `FAILED` status or the restart's rows. Rows it had locked in an uncommitted transaction stay locked until its connection ends. The restart waits for them up to its lock timeout, then fails, and the task retries. The task's `execution_timeout` bounds the one case that recovery cannot resolve: an owner paused between fence and commit.

**Execution tag on the archive connection (ruled 2026-11-11).** The `archive` step's UPDATE of `core.transaction` can wait on a lock held by an online writer. So an operator can tell which session belongs to which execution, the step tags its session. This is observability only.

- **Order.** In the step's fenced transaction, on the connection bound to that transaction, the step reads `CONTEXT_INFO()`, sets the tag, runs its two UPDATEs (`core.transaction`, then `batch.cycle`), sets the value it read back again and reads it back. The fence and COMMIT follow as in section 4.3. No lease statement is added before the UPDATE.
- **Tag.** 24 bytes: the US-ASCII prefix `carddemo-exec-v1` (16 bytes), then the job execution ID of the lease and the poll as an 8-byte big-endian two's-complement value. The helper treats the ID as an opaque 64-bit value: it encodes every bit pattern, 0 and negative values included, as its 8 two's-complement bytes, and it does not check the ID's domain. That is not a public validation and widens no ID domain; the IDs stay the job repository's. A step with no bound execution fails before any SQL, as the fencing transaction manager already requires. The tag holds no PII and no secret. A session matches when its first 24 bytes equal the tag and any further bytes are `0x00`. NULL, an empty value or all zeros means no tag. When there was no prior value, the restore clears with `SET CONTEXT_INFO 0x`, the canonical clear, not `0x00`. That holds once the SQL Server test below (D3 of the archive-tag proposal) shows on the pinned image that `0x` is accepted and reads back as no tag; until then it is not settled, and a different result amends this section rather than the build choosing.
- **Valid IDs and matching (amended 2026-11-11, one rule for the producer, the transport and the validator).** A job execution ID is an integer from 0 to 2^63 − 1. V401 starts `batch.BATCH_JOB_EXECUTION_SEQ` at 0, so 0 is the first execution of a fresh database and is tagged and matched like any other ID. For these IDs the two's-complement bytes are the unsigned bytes, so no reader has to choose a sign. A side that is given an ID to look for (the transport's wait for the blocked archive, infra's admin query, the validator's `Running.execution_id`) accepts 0, and refuses a negative or non-integer ID before any SQL as a usage error, never as a product result. It encodes that ID and compares bytes under the match rule above. It never decodes a session's value back into an ID.
- **One execution per session, cleared before the pool.** A connection carries at most one execution's tag, and only between the set and the restore inside the step's transaction. A prior value that already starts with the prefix is a stale tag and evicts the connection (below). The restore runs before the transaction ends. When it cannot be shown, the connection is evicted after the rollback and before it is handed back to the pool, so a pooled connection never carries the prefix.
- **Statements.** The four tag statements are plain statements whose literal is built from the computed bytes, never from input.
- **Eviction.** The pool does not reset `CONTEXT_INFO`, so the rule of section 4.4's session settings applies. The physical connection is evicted from the pool, never returned, and the step fails, when any of these happens: the read or the set fails; the value read already starts with the prefix; the restore fails; or the read-back differs from the prior value under the rule above. The transaction cannot commit, and the restart repeats the archive. When the UPDATEs themselves fail, the restore still runs. Their exception is the step's failure, and a failed restore is attached to it.
- **Nothing decides on the tag.** The fence, the renewal, the recovery and the poll never read it. Reading another session's tag needs `VIEW SERVER STATE`, which only the admin login holds; `batch_svc` does not. Logs give class names and SQL error numbers, never the tag's bytes, SQL text or a driver message.
- **Scope.** No other step sets a tag. Adding one to another step is a change to this section.
- **Tests:**
  - Without a database: the encoding of 0, 1, `Long.MAX_VALUE`, -1 and `Long.MIN_VALUE` as 8 big-endian two's-complement bytes after the prefix; an observer finds the tag of ID 0 and of `Long.MAX_VALUE` and refuses -1 before any SQL; the clear statement `SET CONTEXT_INFO 0x` when there was no prior value; the statement order; each of the four failures evicts and does not run the UPDATEs, or runs no more SQL after them; a foreign prior value is restored byte for byte; a failed UPDATE keeps its own exception; no driver message reaches a log.
  - On SQL Server: an archive UPDATE blocked by a held key lock shows the tag of its job execution ID in `sys.dm_exec_requests` next to the blocker. After the job, every pooled connection, all borrowed at once, has no tag. Killing the blocked session fails the step, and no pooled connection carries the prefix. The length and padding that `CONTEXT_INFO()` and the views return are recorded, and the match rule above holds for them. The semantics test (D3 of the archive-tag proposal) also records what `CONTEXT_INFO()` and `sys.dm_exec_sessions.context_info` return after `SET CONTEXT_INFO 0x` on a session that had a tag; it passes when that is no tag.

### 4.6 Suspend and pause behaviour

A laptop that sleeps suspends Airflow, batch-service and the SQL Server container together. On resume, the database clock jumps by the sleep time, and the JVM's scheduler may fire its next renewal up to one interval later. After a sleep longer than TTL + grace, a launch that runs before that renewal can recover a live owner. Fencing keeps this safe: the owner's next commit fails, and the restart resumes after the last committed chunk. The cost is one restart, never a double apply. This behaviour is verified, not assumed:

- In CI (Linux): `SIGSTOP` the batch-service JVM for less than TTL + grace, then `SIGCONT`. Expected: no recovery, and the job completes. Repeat for longer than TTL + grace with a launch during the stop. Expected: one recovery, the owner's next fence fails, and the results equal an uninterrupted run.
- Once on the macOS dev host, recorded in `verify-cycle`'s notes: put the host to sleep (`pmset sleepnow`) during `post` for 30 s and again for 5 minutes. Record how the container's `SYSUTCDATETIME()` and the JVM renewal behaved, and whether a recovery happened. If the database clock does not jump on this platform, record that too. Either way, the result must equal an uninterrupted run.

### 4.8 Output publication

This rule applies to every output a job writes under its instance root ([section 4.10](#410-output-root-ruled-2026-11-11)): statements, the transaction report, the category balance listing, the export and the rejects file. It replaces the earlier rule that a restart replaces a leftover temporary folder and an existing target. That rule let an owner that had lost its lease rename or overwrite its successor's output.

- **Working paths per execution.** Each execution writes only under a path that contains its own job execution ID: `<kind>/.work/<id>.<jobExecutionId>/` for a folder, and `<name>.<jobExecutionId>.tmp` beside its target for a single file. No two executions share a path.
- **No-replace publication (revised 2026-11-11).** No publication renames anything, and nothing is ever created with `REPLACE_EXISTING`. `Files.move` with `ATOMIC_MOVE` is POSIX `rename(2)` on Linux and macOS, which replaces an existing file and an empty directory at the new name, so it is not a no-replace operation and no publication uses it. Every published name is created by an operation that fails when the name exists: `Files.createDirectory` (`mkdir(2)`) for a folder, and `Files.createLink` (`link(2)`, which also fails on a symbolic link at the new name) for a file. The publisher decides from the result of that operation. An existence check made before it may shorten the path, but it never decides.
  - **A single file** (the rejects file, the transaction report, the category balance listing, the import's reject file). Its folder `<kind>/<id>/` is created with `createDirectory`, mode `0700`. When it exists already, it must pass the path checks (a directory, not a symbolic link, owned by the service user, no group or other bit), or the step fails with `OUTPUT_PERMISSIONS`. That folder alone is not an output. The working file `<name>.<jobExecutionId>.tmp` is written in it and hashed, and then published with `createLink` onto `<name>`. The publisher decides from that result. When `<name>` exists, it must be a regular file that passes the path checks, or the step fails with `OUTPUT_PERMISSIONS` and leaves it untouched. It must also hash to the expected sha256 (the intent's, or for the rejects file the working file's): equal bytes continue, other bytes fail with `PUBLICATION_MISMATCH` and keep the working file. When the working file is missing (another publisher of the same intent linked it and removed it), the target decides: it must exist and hash to the intent's sha256, otherwise `PUBLICATION_MISMATCH`; a job without an intent (the rejects file) fails with `PUBLICATION_MISMATCH`. Then the working file is removed; one that is already gone is not an error.
  - **A folder** (statements, the export). The output is a flat set of regular files plus its manifest `MANIFEST.sha256`: one line `<sha256>  <file name>` (lower-case hex, two spaces, LF) for every other file, sorted by name in byte order. File names match `[A-Za-z0-9._-]+`, do not start with a dot and are never `MANIFEST.sha256`. The folder's sha256 is the sha256 of its manifest. The publisher:
    1. reads the manifest and checks that its sha256 is the intent's: the working folder's manifest, or, when that is missing, the final folder's `.claim`. When neither exists, the step fails with `PUBLICATION_MISMATCH`. Every other entry of the working folder must be a listed regular file; a listed file may be missing, and step 4 decides. A working folder that is gone when it is listed, or that vanishes during the listing, has no other entries, and an entry that vanishes before its type is read is not an entry: another publisher of the same intent removes them in step 7. Neither fails the step, which goes on to step 2;
    2. creates the final folder `<kind>/<id>/` with `createDirectory`, mode `0700`. When it exists already it must pass the path checks, or `OUTPUT_PERMISSIONS`. An existing final folder is joined, not owned: it may be one that a crashed or concurrent publisher started. Before it claims, the publisher may list a joined folder and fail with `PUBLICATION_MISMATCH` when it holds a name other than `.claim`, `MANIFEST.sha256` and the listed files. Step 6 would fail on that name in any case, so failing early changes only one thing: nothing is linked;
    3. claims the final folder before it links any other file: it creates `<kind>/<id>/.claim` with `createLink` from the working manifest. When the link fails because `.claim` exists, or because the working manifest is gone (missing at step 1, or removed since by another publisher of the same intent), the publisher reads `.claim` in the final folder. It must be a regular file that passes the path checks and hashes to the intent's sha256: then the publisher joins a publication of its own intent. A `.claim` that is absent at that read, or that has other bytes, fails the step with `PUBLICATION_MISMATCH`. A `.claim` that is present but is not a regular file passing the path checks fails it with `OUTPUT_PERMISSIONS`. In either case nothing is linked. `link(2)` either creates the name or fails, and `.claim` is never rewritten, replaced or removed (retention removes it only with its whole folder), so the first claim binds the final folder to one intent for good. A publisher of any other intent fails here, before it links a file, whatever the interleaving. No other lock is needed or assumed;
    4. for each listed file, in manifest order, hashes the working file against its line and creates the file in the final folder with `createLink` from the working file. A working file with other bytes fails with `PUBLICATION_MISMATCH` and is not linked. When the working file is missing, vanishes before it is hashed, or the link fails because its source is gone or because the name exists, the publisher reads the final name: present, it must be a regular file that passes the path checks, or `OUTPUT_PERMISSIONS`, and must hash to its line, or `PUBLICATION_MISMATCH`. Either way it is kept as it is; absent, the step fails with `PUBLICATION_MISMATCH`. No check made before the link decides that a name is there or not;
    5. links the manifest `MANIFEST.sha256` last, with `createLink` from `.claim` (the same bytes), and handles an existing name as in step 4, against the intent's sha256. The manifest in the final folder is the completion marker. A final folder without it is incomplete: no reader uses it, and only a publisher whose intent matches its `.claim` completes it;
    6. verifies the final folder: it holds exactly the listed files, the manifest and `.claim`, each a regular file that passes the path checks and hashes to its line, and the manifest and `.claim` hash to the intent's sha256. A listed file, the manifest or `.claim` that is not a regular file passing the path checks fails with `OUTPUT_PERMISSIONS`. An extra entry of any type, a missing file or another hash fails with `PUBLICATION_MISMATCH`. Nothing is removed or replaced;
    7. only then removes the working files that the manifest lists, the working manifest and the working folder. A file that is already gone is not an error: another publisher of the same intent removed it. Any other entry in the working folder is left in place with its folder, is never published, and is counted in the step's log (Logs, below).

    Only a publisher whose intent matches `.claim` links into a final folder, and it links only listed names, so no file is added to a final folder once its manifest is linked. `.claim` belongs to the publication, not to the output: it is not a manifest line, readers never serve it, and clean-up never touches it. Readers find files only through the run that the job's completing transaction recorded, never by listing the folder.
  - **Which code (D1, 2026-11-11).** One rule applies at every name that a publisher reads or links: a single-file target, `.claim`, a listed file and the manifest. A name that is present but is not a regular file passing the path checks (a symbolic link, a folder, another type, another owner, a group or other bit) gives `OUTPUT_PERMISSIONS`. A regular file that passes them but has other bytes gives `PUBLICATION_MISMATCH`. A name in a final folder that the manifest does not list gives `PUBLICATION_MISMATCH`, whatever its type. Nothing is repaired, replaced or removed in any of these cases.
  - **Hard links.** A working path and its target are under the same instance root, on one file system. A link that fails for any reason other than an existing name (`EXDEV`, `EPERM`, ...) fails the step. There is no copy fallback. A working file and its published names are one inode, so a write through the working path after the link would change the published bytes. Every working file, the working manifest included, is therefore written only before its intent is committed, closed and forced to disk before it is hashed, and never opened for writing again.
  - **Concurrent publishers.** Two publishers of the same intent end with one complete final folder, whichever of them links each name first, and both verify it. Two publishers with different bytes for one target cannot both hold a committed intent (one intent per instance), but a reissued ID after a restore (section 4.10) can meet another intent's final folder. Whatever the interleaving, the first `.claim` linked decides (step 3): the other publisher fails with `PUBLICATION_MISMATCH` before it links any file. So a final folder only ever holds files of the intent its `.claim` names, no file is replaced, and a final folder that does not verify is never recorded as published.
  - **The output root is not an output.** Its creation (section 4.10, `ensure`) keeps its rename of a non-empty sibling: the rename can replace only an empty directory, and `ensure` then checks the root's own marker.
- **An existing target.** When the target already exists, the publisher compares sha256 values. Equal bytes mean an earlier execution already published the same output, and the job continues. Different bytes fail the job with `PUBLICATION_MISMATCH`, and nothing is replaced. No job writes, replaces or deletes a published output; retention removes it under its own rule.
- **Committed intent, or inputs fixed for the instance.** The equal-bytes check above is sound only when every execution of an instance builds the same bytes. So every job that writes an output is in exactly one of these groups:
  - **Intent in the run row: `statementJob`.** It commits the intent before it publishes: the working path and the sha256 values go into the row in a fenced transaction (`PUBLISHING`), then the links of the folder publication above, then a fenced completing transaction (`COMPLETED`) after it hashes the target again ([batch.md](batch.md#runs-restart-and-rerun)).
  - **Intent in the job execution context: the transaction report, the category balance listing and the export.** Their inputs can change between two executions of one instance (posting, the master archive and online writes change the rows they read), so a second execution may build other bytes. Each writes its output into its working path, hashes it (the file, or the manifest of a folder), and commits `{workPath, sha256}` into the Spring Batch job execution context in a fenced transaction. It publishes only after that commit succeeds: in the publish transaction of [section 4.3](#43-fence), or outside any transaction followed by a fenced recording transaction. Spring Batch saves the job execution context on its own only between steps, outside the step's fenced chunk transaction. So the step writes the intent with an explicit `JobRepository.updateExecutionContext(jobExecution)` inside its fenced transaction. The job repository uses the plain transaction manager that the fencing manager wraps, over the same data source, with `REQUIRED` propagation, and the lost-execution decorator of section 4.5, so the call joins the fenced transaction. A test loses the lease at the intent commit, then checks that `BATCH_JOB_EXECUTION_CONTEXT` holds no intent and that the restart builds again. Spring Batch carries the job execution context into a restart. A restart that finds an intent builds nothing: when the target exists it verifies it against the intent's sha256 (a final folder whose `.claim` matches is completed first, as above), and otherwise it verifies the named working path and publishes it. A missing or different file fails with `PUBLICATION_MISMATCH`. For these jobs a target that exists with no committed intent also fails with `PUBLICATION_MISMATCH`.
  - **No intent, inputs fixed: the daily rejects file.** Its rows are final when the `post` step ends, and its read is scoped to its own attempt: one statement reads `batch.cycle` for the `cycle_id`, left-joined to its `core.daily_reject` rows, and returns the cycle's current `attempt` with them. The step decides from that one result. When the current attempt is not the instance's `attempt` (a `cycle-rerun` has run), the step fails with `CYCLE_ATTEMPT_CHANGED` and writes nothing. An attempt with no rejects returns the cycle row with no reject columns and writes an empty file. A separate attempt query is not allowed, because a rerun between the two would let a stale owner write an empty file for the old attempt. So a stale attempt-1 owner never writes attempt 2's rows. The equal-bytes check then holds for every execution of the instance.

  A lost lease rolls an intent back, so a stale owner's path is never named. A restart that finds an intent committed finishes it and does not build again. A job that is added later, including the export's completeness manifest and the import's error file, is placed in one of these groups before it is built.
- **Clean-up.** A start deletes only working paths of its own instance whose execution is terminal and that no committed intent names. A path that a recovered owner creates or writes into later is debris of the same kind: it is never published, and the next start of the instance removes it. Removing a working path removes only its names: a final folder, its `.claim` and its files keep their links. A start deletes nothing else.
- **Logs (ruled 2026-11-11, D-10).** Every log line, warning, exception message and exit description that the output publication and the clean-up write (the shared library and every job that uses it, the statement job included) carries only: a fixed reason code from a closed set that the library defines, counts (for example, how many entries were kept or appeared late), the output kind, and the run ID and job execution ID. It never carries an entry name, a file name, a relative or full path, a hash of a single entry, or any part of a file's contents. A name in these folders can be personal data: fixed-mode statements name files `<acct_id>.pdf`, and an extra entry can have any name. The IDs say which folder it is. An operator who needs the names inspects the instance root, which is `0700`, privately with the service user's or the admin's access. A test puts an entry with a sentinel name into a working folder for each logged case (an unlisted entry at step 7, an entry that appears during a clean-up, a refused clean-up, `PUBLICATION_MISMATCH` and `OUTPUT_PERMISSIONS` at a listed name) and checks that the captured log and the exceptions hold the code and the count and never the sentinel.
- **Permissions.** One rule, the one of [section 4.10](#410-output-root-ruled-2026-11-11) (path checks), applies to every path here. New folders are created with mode `0700` and new files with `0600`. The mode is given at creation only, with the restrictive attribute (`PosixFilePermissions.asFileAttribute`). The umask can only remove bits from it, so no new path ever has a wider mode, and no mode is set afterwards. At start, batch-service checks the instance root, each output root it writes (`statements/`, `reports/tranrept/`, `reports/prtcatbl/`, `exports/`, `imports/`, `rejects/`, `dailytran/archive/`) and their `.work/` folders. A path that is not a directory, is a symbolic link, is not owned by the service user (section 4.10) or has any group or other permission bit fails the start with `OUTPUT_PERMISSIONS`. It is never repaired: no process changes the mode or owner of an existing path.
- **The report download.** Locally every JVM runs as the same OS user, so transaction-service can read these `0600` files under `reports/tranrept/` of the same instance root (section 4.10). A deployment that runs transaction-service as another user needs the deployment decision of section 4.10 (deployment as another user).
- **Serving.** A download resolves its file from a completed run row, never through a directory listing or a caller's path. The transaction report has no file-name column: its path is derived from the run row's ID, `reports/tranrept/<report_run_id>/TRANREPT.txt` under the instance root, and its bytes are checked against the row's `output_sha256` before any is sent (section 4.10). A statement file is found through its `batch.account_statement.file_name` and checked against its `file_sha256`.
- **Database reset.** Superseded by [section 4.10](#410-output-root-ruled-2026-11-11): a recreated database writes into a new instance root, so no reset refuses because outputs exist. No tool deletes or moves outputs. The inbound archive copies are under the instance root too.

### 4.9 Inbound daily file

The inbound file `dailytran/<businessDate>.txt` under `<CARDDEMO_VAR_DIR>/inbound/` ([section 4.10](#410-output-root-ruled-2026-11-11)) belongs to the operator. No job moves, renames, rewrites or deletes it. This replaces the earlier rule that `ingestDailyFileJob` moved it to the archive after its last commit, which let a stale owner move the next attempt's input.

1. **Copy.** At `stage` start, when the cycle has no stored file identity for its attempt, the execution copies the inbound file to `dailytran/archive/.work/<businessDate>.<attempt>.<jobExecutionId>.tmp` under the instance root ([section 4.10](#410-output-root-ruled-2026-11-11)) and hashes the copy. The temporary file is created with `CREATE_NEW` and mode `0600` from the start (section 4.8, permissions). If it already exists, the step fails with `PUBLICATION_MISMATCH` and leaves the file in place: within one instance, job execution IDs are never reused, so an existing file is not this execution's. The copy's sha256 `H` is the attempt's identity. The attempt never reads the inbound file again.
2. **Publish the copy.** `Files.createLink` onto `dailytran/archive/<businessDate>.<attempt>.<H>.txt` under the instance root, never replacing. When that name exists, its bytes must hash to `H`; otherwise the step fails with `PUBLICATION_MISMATCH`. Then the execution removes its temporary file.
3. **Commit the identity.** One fenced transaction stores the file name and `H` on `batch.cycle`, compare-and-set on "no identity stored for this attempt". With 0 rows another execution stored one first, and this execution uses the stored identity.
4. **Stage.** `stage` reads only the archive copy that the stored identity names, and checks its sha256 at every start and restart. A missing copy fails with `DAILY_FILE_NOT_FOUND`; a different hash fails with `DAILY_FILE_CHANGED`.

A stale owner's copy whose identity was never committed is debris: its name carries its own hash, no step reads it, and it changes neither the inbound file nor another attempt's copy. Archive copies are kept with their cycle and removed only by the retention rule (D-BAT-04). The end-of-job move (`ArchiveDailyFileTasklet`) is replaced by steps 1 to 3.

**`cycle-rerun`** (`CycleRestore`). The inbound file is still in place, so the rerun returns nothing in the normal case, and the next attempt archives whatever file is inbound then (a corrected file, if the operator replaced it). Only when the inbound file is missing does it put back the copy that the replaced attempt's stored identity names. Inside the restore's transaction, after it locks the cycle's row and before the remaining checks, it reads that identity, copies the archive file to a temporary name unique to the invocation (`<name>.rerun.<uuid>.tmp`, mode `0600`) and checks the copy's hash against the identity; a different hash refuses the rerun with `DAILY_FILE_CHANGED`. After the remaining checks and the restore, it links the copy onto the inbound name with no replace (an inbound file that appeared meanwhile is kept), as the last change before the commit. The temporary file is removed on every path the process survives, so a refused rerun puts nothing back and leaves no temporary file; a crash can leave a `<name>.rerun.<uuid>.tmp` that no step reads. The file system and the database are not changed atomically: if the commit fails after the link, the file is inbound with the stored hash and the cycle is not restored, and the next rerun keeps that inbound file. When the replaced attempt has no stored identity, nothing is returned ([batch.md](batch.md#data-load-admission-and-the-reruns-refusals-ruled-2026-11-11), the daily-file return).

Tests: owner A is paused after its copy, recovered, and B stages; A resumes, its identity commit fails its fence, and the inbound file and B's copy are unchanged. A rerun with a corrected inbound file stages the corrected file as attempt 2 under its own hash, and attempt 1's copy is unchanged. Two prepared returns at once use different temporary names, and the inbound file ends with the archived bytes. A changed archive copy fails the restart with `DAILY_FILE_CHANGED`. A rerun refused after the return was prepared, by each refusal in turn, puts no file back and leaves no temporary file. An archive copy that cannot be read fails the preparation and the rerun, and leaves no temporary file (POSIX, not as root).

### 4.10 Output root (ruled 2026-11-11)

#### Setting

- **One setting: `CARDDEMO_VAR_DIR`, absolute.** It is resolved in this order: the process environment, then the shared `.env`, then the computed default `<main checkout>/modernization/var` (the main checkout is the worktree that owns `.git`, as the Makefile and `with_env.py` find it today). The Makefile reads the `.env` value before it falls back to its computed default. The Makefile, `scripts/stack.py`, `scripts/with_env.py`, `scripts/batch_e2e.py`, `scripts/e2e_stack.py` and Airflow pass the resolved value to every process they start. In the JVMs it is the property `carddemo.var-dir` (`${CARDDEMO_VAR_DIR:}`). A service, db-migrate or an Airflow task without it, or with a relative value, fails with `OUTPUT_ROOT_INVALID`, so the working directory never matters. At start each JVM resolves it once to its real path (`toRealPath()`). The setting itself may be a link that the operator chose. Everything below it is checked (O7).
- **Inbound is derived (O5).** The inbound folder is `<CARDDEMO_VAR_DIR>/inbound/`. It is never set on its own. batch-service's `carddemo.batch.files.inbound-dir` and `CARDDEMO_INBOUND_DIR` are removed with their relative default `var/inbound`. `carddemo_airflow/cycle.py` loses its fallback `"var"`. When the setting is missing or relative there, the task fails with `AirflowFailException("CARDDEMO_VAR_DIR is unset or relative")`, so batch type maintenance is never skipped silently because of the working directory.
- **`make setup` fills it, add-only.** `.env.example` lists `CARDDEMO_VAR_DIR=` with an empty value, so no source file holds a home path. `scripts/init_env.py` writes the computed absolute default when `.env` lacks the key or has it empty, as it fills generated secrets today. It never changes a value that is set. A set value that is relative makes setup print `FAIL  CARDDEMO_VAR_DIR must be an absolute path` and end `setup: FAILED`, and the value is left unchanged. The key is a path, not a secret: setup prints the value it wrote, and the secret rule (`*_PASSWORD`, `*_SECRET`, ...) never touches it.
- **Old settings refused.** These settings are removed with their defaults:
  - the variables `CARDDEMO_OUTPUT_DIR`, `CARDDEMO_REPORTS_DIR`, `CARDDEMO_TRANREPT_DIR` and `CARDDEMO_INBOUND_DIR`;
  - the properties `carddemo.batch.files.output-dir`, `carddemo.batch.files.inbound-dir` and transaction-service's report root.

  When one is set anyway, in the environment, in `.env` or as a property, setup prints a `FAIL` line naming it. It does not delete the key, because setup is add-only. batch-service, transaction-service and db-migrate fail their start with `OUTPUT_ROOT_LEGACY_SETTING: <name> is no longer read; remove it (outputs are under CARDDEMO_VAR_DIR/out/)`. The message names the setting only, never its value. `scripts/stack.py` stops setting them.
- **Private folders for tests (O8).** Only the demo stack writes into the shared `CARDDEMO_VAR_DIR`.
  - JVM tests that write outputs set `carddemo.var-dir` to a JUnit `@TempDir` (mode `0700`), which JUnit removes after the test.
  - `scripts/batch_e2e.py`, `test-batch-live`, `scripts/e2e_stack.py` and the `verify-batch` harness create a private folder with `tempfile.mkdtemp()` (mode `0700`). They pass it as `CARDDEMO_VAR_DIR` to the batch-service and transaction-service they start, and remove it when they end. `KEEP_VAR=1` keeps it and prints its path.
  - The harness's own lock (`run/heavy.lock`), logs and PID files stay in the shared folder, because they are machine-wide.

  Removing such a folder is the only deletion of outputs that any tool does, and it deletes only a folder that the same run created.

#### Instance and root

- **Instance marker table.** Data owns the migration, `V420__ops_database_instance.sql`. The orchestrator has confirmed the version. Its exact DDL is in 4.10.1. `batch_svc` and `transaction_svc` get `SELECT` on it in `R__grants_batch.sql` and `R__grants_transaction.sql`. Backend is the one owner of both grants and of their login probes; `V420` (data, `f4b35f6`) grants nothing. No service login gets `UPDATE`, `INSERT` or `DELETE`. Only db-migrate, as the database owner, rotates it (O4).
- **Create paths.** Every way of creating a database runs the migrations, so every new database gets a new ID, with no check of its own to forget. The review confirmed each one:
  - `db-reset`: `recreateDatabase`, then migrate;
  - `db-migrate` on a missing database: `ensureDatabase` after `infra-wipe`;
  - `TestDatabase`: recreate, logins and migrations, once per test JVM;
  - `verify-migrations`' scratch databases;
  - `batch_e2e.py` through `db-reset`;
  - a database created by hand and migrated.

  No main code reseeds an output ID inside a live instance. The copies of an earlier instance's state (restore, attach, volume copy) keep the marker. They are handled by the rotation (O4).
- **Upgrade of an existing database (O10).** An existing database that gets the migration as an upgrade gets a new ID once. Its earlier outputs are in the pre-instance layout: directly under `CARDDEMO_VAR_DIR` (`rejects/`, `reports/`, `statements/`, `exports/`), and the daily-file archive under the inbound root, `<CARDDEMO_VAR_DIR>/inbound/dailytran/archive/`, which holds daily transactions with card numbers. They are kept, listed and never read. Rejects written before the change went to `${CARDDEMO_OUTPUT_DIR:var}` relative to batch-service's working directory, and `scripts/stack.py` never set that variable, so such files can sit under a module folder. The listing does not find them, and the operator removes them by hand under retention. A completed run from before the upgrade gets the missing-file answer.
- **Instance root.** `<CARDDEMO_VAR_DIR>/out/<database component>/<instance id>/`. The rendering of both parts is fixed in 4.10.2 (O3). Every output path of sections 4.8 and 4.9 is under it: `statements/`, `reports/tranrept/`, `reports/prtcatbl/`, `exports/`, `imports/`, `rejects/`, `dailytran/archive/`, and their `.work/` folders.
- **Atomic creation (O2).** `ensure` never exposes a root without its marker:
  1. It creates `out/` and `out/<database component>/` if they are missing (mode `0700`).
  2. It creates the sibling `out/<database component>/.<instance id>.<random UUID>.tmp/` (`0700`).
  3. It writes the canonical `.instance` into it with `CREATE_NEW` (`0600`) and forces it to disk.
  4. Just before the rename it reads the root path without following links. When the path is a symbolic link, it gives `OUTPUT_PERMISSIONS` and does not rename.
  5. It renames the sibling onto `<instance id>` with `ATOMIC_MOVE`, never with `REPLACE_EXISTING`. On Linux and macOS this is POSIX `rename(2)`. It fails on a non-empty directory (`ENOTEMPTY` or `EEXIST`), and every completed root holds `.instance`. It fails on a file (`ENOTDIR`). It replaces only an empty directory, which holds no data. So a target that holds data is never replaced. Native `renameat2` or `renamex_np` is not used.
  6. After a successful rename it checks, in this order: that its sibling is gone, otherwise `OUTPUT_ROOT_INVALID`, with the sibling left in place; that the root passes the path checks below, otherwise `OUTPUT_PERMISSIONS`; and that the root's `.instance` equals this process's own marker bytes, otherwise `OUTPUT_ROOT_INCOMPLETE` when it is missing and `OUTPUT_ROOT_MISMATCH` when it differs.

  When the rename fails because a directory is at the root path, the helper removes its own sibling, and only that one, and validates the winner's marker. A file at the root path gives `OUTPUT_PERMISSIONS`. A crash before the rename leaves only a sibling, which is never read, never blocks a later `ensure` (that uses a new random name) and is listed with the old roots. So no crash poisons the instance.
- **Validation.** Whenever the helper finds the root, the following rules apply. In each failing case nothing under the root is read or written.
  - **Marker matches.** The root's `.instance` must equal the canonical marker bytes of this database's identity, byte for byte. A different marker gives `OUTPUT_ROOT_MISMATCH`. A copied or foreign tree is therefore never used.
  - **Marker missing.** An existing root directory with no `.instance` gives `OUTPUT_ROOT_INCOMPLETE`. It is reported, never repaired, and the runbook says how the operator resolves it. With the atomic creation, only an action outside the protocol can produce such a root.
  - **Path checks (O7).** This is the only permission rule, and section 4.8 applies it to the output folders below the root. It covers `out/`, `out/<database component>/`, the root and its `.instance` marker. Each directory must be a directory, and the marker a regular file. None may be a symbolic link, and each must be owned by the service user and have no group or other permission bit. Anything else gives `OUTPUT_PERMISSIONS`, reported and never repaired: no process changes the mode or owner of an existing path. New directories are created `0700` and new files `0600`.
  - **Service user (F9).** The service user is the owner of a file the process has just created: `unix:uid` where the file system offers it, otherwise the `FileOwnerAttributeView` owner. Each JVM finds it once, lazily, at its first path check: it creates a `0600` probe file in `java.io.tmpdir`, reads its owner and deletes the file. The `user.name` property is never used, because a launch option can override it and a container with an arbitrary UID does not name the process user with it. Nothing above `CARDDEMO_VAR_DIR` is checked: the setting is resolved once with `toRealPath()`, so operating-system aliases above it (on macOS, `/tmp` to `/private/tmp` and `/var` to `/private/var`) are never refused. The output folders below the root keep section 4.8's rules.
  - **Limit A-1: inheritable ACLs (ruled 2026-11-11, security sign-off of output-root v9 section 9).** The path checks see only the owner and the mode bits. On macOS, an inheritable access-control entry (`file_inherit`, `directory_inherit`) on `CARDDEMO_VAR_DIR` or on an ancestor is copied onto every folder and file created below it, whatever the create mode: a `0700` folder and a `0600` file then pass the path checks while another principal can list, read or write them. That covers every instance root and its outputs (statements, reports, exports and imports, rejects and the daily-file archive, which hold PII) and the report download's staging folder. On Linux a POSIX default ACL gives a named entry no effective access under the `0700`/`0600` create modes, because the mask follows the group bits that the check reads (from acl(5); not verified on a Linux host); NFSv4 and ZFS ACLs are outside the supported local POSIX file systems. The JDK has no ACL view on macOS or Linux, so `platform/output-root` cannot detect such an entry without native code, and none is added. So the rule is a stated precondition with an operator check, not a module check: `CARDDEMO_VAR_DIR`, the staging base of transaction-service ([transaction-service.md](transaction-service.md#16-report-download-checks-the-committed-sha256-2026-11-11) item 3.5: `CARDDEMO_VAR_DIR` for the default, the override's parent otherwise) and their ancestors carry no inheritable entry that allows access to another principal.
    - **Operator check (infra).** `make setup` and the stack's start preflight (`make up`, before any service starts) check, on macOS with `ls -led`, and on Linux with `getfacl` where it is installed: `CARDDEMO_VAR_DIR`, the staging base, and `out/` and the staging folder when they exist. An `allow` entry with `file_inherit` or `directory_inherit` for any principal other than the service user (on Linux, a `default:` entry for a named user or group with any permission) is a `FAIL` line: `setup` does not end `OK`, and `make up` refuses to start. On `out/` and the staging folder an inherited entry also fails: it shows that files below were already created exposed, and the operator then investigates what was readable. The same entries on a higher ancestor give a `WARN` line only, because a system folder above the setting is outside the operator's control and the entry on the setting itself is what reaches new paths. Where `getfacl` is missing, the check prints one line saying it was skipped, and never passes silently. The lines name the setting (`CARDDEMO_VAR_DIR`, `carddemo.transaction.report.staging-dir`), the fixed relative name (`out/`), the principal and the permission, and no path below `CARDDEMO_VAR_DIR` (Messages outside the root). Nothing is repaired: the operator removes the entry (`chmod -a` on macOS, `setfacl -k` on Linux). Tests (infra): on macOS, a temporary `CARDDEMO_VAR_DIR` given `chmod +a "group:everyone allow list,add_file,search,read,file_inherit,directory_inherit"` fails both targets, the same entry on its parent only warns, a deny entry and an entry for the service user pass, and an inherited entry on `out/` fails.
    - **Owners.** Infra: the operator check in `make setup` and `make up`, with its tests, and the rows of [make-targets.md](make-targets.md). Backend: A-1 stated as a limit in its output-root contract (document v10, section 3, done), and the confirmation that no ACL view exists for the module (`AclFileAttributeView` is Windows-only), in that contract. Transaction-service (backend): the limit in its residuals ([transaction-service.md](transaction-service.md#16-report-download-checks-the-committed-sha256-2026-11-11) item 7). #### Who resolves when (O1, O6, bootstrap)

No process caches the root at start. Each use reads the identity from the database again, on the connection that does the work.

- **db-migrate creates the root.** After it migrates, `DbMigrateApplication` reads the identity and calls `ensure`. So `make db-reset` and `make db-migrate` end with the root and its marker in place, and so does every target that runs them (`make billpay` on an empty database, the e2e scripts). db-migrate prints the root, and lists the earlier roots, the leftover siblings and the pre-instance outputs of this database name, with their file counts, as kept and no longer read.
- **batch-service binds each execution to one instance.**
  - **At start**, the server and every one-shot JVM (`load`, `cycle-rerun`, the CLI commands) run `ensure` and the permission checks. A failure fails the start.
  - **At the first start of a job execution**, the launch transaction reads the identity and calls `ensure`. It stores `outputRoot.database` and `outputRoot.instanceId` in the job execution context, with the explicit `updateExecutionContext` of N7.
  - **The fence check.** Every fenced transaction that comes before writing or publishing an output reads `instance_id` again in the same transaction and compares it with the bound value. These are: each step's start, each intent commit (section 4.8), the statement run's status compare-and-set, the inbound identity commit (section 4.9) and each completing transaction. When the value differs, the transaction rolls back and the step fails with `OUTPUT_ROOT_MISMATCH` before any further write or publish.
  - **Bound root only.** Writes go only to the bound root. The root is never derived again in the middle of an execution. A restart reads the bound value from the context and runs the same comparison.
  - **Effect of a reset.** A `db-reset` under a running batch-service therefore never lets an execution write into the new instance's names. The new instance's first launch binds the new root.
- **transaction-service only reads and never fails its start because of the root (O6).** Its start fails only for an invalid `CARDDEMO_VAR_DIR` (`OUTPUT_ROOT_INVALID`) or a legacy setting (`OUTPUT_ROOT_LEGACY_SETTING`). Otherwise it starts, reports healthy and serves every view that does not download a file, whether or not batch-service has started and whether or not the root exists. Each report download is handled like this:
  1. It reads the run row and the identity in one statement, so both come from the same instance, also after a reset while the service runs:

     ```sql
     SELECT r.status, r.output_sha256, DB_NAME() AS database_name, CONVERT(CHAR(36), i.instance_id) AS instance_id
     FROM batch.report_run r CROSS JOIN ops.database_instance i
     WHERE r.report_run_id = ? AND i.id = 1
     ```

  2. It builds the `Instance` from that row and calls `resolve`, which checks the marker and the managed paths in that same request. The result is never cached.
  3. For a `COMPLETED` row only, it reads `<root>/reports/tranrept/<report_run_id>/TRANREPT.txt` and serves it only when its bytes hash to the row's `output_sha256` (V424). The path checks of `existingFile` run first. Then the file is opened once and never by path again: it is copied into a private snapshot with no name in the file system, which is read back, hashed, checked and served through one channel, with fixed buffers and no size limit ([transaction-service.md](transaction-service.md#16-report-download-checks-the-committed-sha256-2026-11-11)). A `COMPLETED` row with no `output_sha256` (completed before V424), a snapshot that cannot be made, and a file whose hash differs fail closed with the missing-file answer, before any header or byte of the body is sent. Nothing infers, backfills or repairs a hash, and the file and the row stay as they are.

  A missing root or file gets the existing missing-file answer. A mismatch, an incomplete root or a permission failure fails that download closed with the same answer and logs the code. It never falls back to another path or root, and it never creates anything. So a new instance's run 1 can never serve an earlier instance's `1/TRANREPT.txt`.
- **Start order.** `make up` starts the online services, then batch-service, then Airflow, as `stack.py` does today, and no online service waits for batch-service. On a fresh clone the sequence is `make setup`, `make infra-up`, `make db-reset`, `make load`, `make up`. db-migrate has created the root before any service starts, and `load` validates it. A database migrated by another path gets its root at batch-service's first start. Until then, a download gets the missing-file answer, and a completed report downloads afterwards with no restart, because the root is resolved per download.
- **Two databases at once.** The demo database and `carddemo_batch_e2e` (or any test database) have different names and IDs, so their roots never overlap, even with one `CARDDEMO_VAR_DIR`.

#### Restore and rotation (O4)

On SQL Server, `RESTORE ... WITH REPLACE` over the same database keeps `sys.databases.create_date` and `database_guid`. It also rolls the identity and sequence values back, and so hands out again every ID issued after the backup. The review found this, and the architect reproduced it on the stack's SQL Server 2025 with a scratch database. So database metadata cannot detect a restore, and the restored marker names the same root.

- **Integrity does not depend on the rotation; availability does.**
  - **Without rotation:** a reissued run ID finds its target and fails with `PUBLICATION_MISMATCH` (section 4.8), a reissued job execution ID meets an existing working path and fails (`CREATE_NEW`, section 4.9), and downloads serve only `COMPLETED` rows, whose files are from before the backup. So no wrong bytes are served or replaced. Runs fail until the rotation.
  - **Clean-up:** a start's clean-up (section 4.8) deletes a working path only when its job execution exists in this database and is terminal. An execution ID that the database does not know is never deleted. The rule protects only those IDs. When one backup is restored on two servers that share a folder, both can issue the same ID again. Server A's execution then fails on B's working path (`CREATE_NEW`) and becomes terminal, and A's next start can delete B's working path for that ID. Integrity still holds, because B's restart finds its named path missing and fails with `PUBLICATION_MISMATCH`. Availability does not: the rotation is what restores it.
- **Owned procedure: the runbook `docs/runbooks/modernized-database-restore.md`.** Infra writes it, with its tests. The steps are:
  1. `make stop` (the services and Airflow).
  2. Restore with SQL Server's `RESTORE` (or attach the copy).
  3. `make db-migrate NEW_INSTANCE=1`. This is db-migrate's `--new-instance` option, owned by backend. After the migrations it runs the rotation statement of 4.10.1 as the database owner, then `ensure`. It prints the new root and lists the old one as kept.
  4. `make up`.

  The runbook also says how to resolve `OUTPUT_ROOT_INCOMPLETE`: move the incomplete folder aside by hand, then run `make db-migrate`. Outputs of the previous instance stay in its root and are no longer served; their runs get the missing-file answer and can be run again. An execution bound to the old instance fails with `OUTPUT_ROOT_MISMATCH` on restart. The remedy is `cycle-rerun` or a new run.

#### No automatic delete

No tool, target, job or service deletes, moves or rewrites an instance root, an old root, a leftover sibling or a pre-instance output. There are three exceptions, each on paths that the deleting process or run created itself:

- section 4.8's clean-up of terminal working paths;
- `ensure` removing its own sibling after a lost rename;
- a test harness removing the private `CARDDEMO_VAR_DIR` it created (O8).

Removing an old root is an operator action under retention (D-BAT-04). This supersedes the refusal of the P4 preflight, which the review accepted with O1. Its "no clear" decision stands.

#### Deployment as another user (O9; documentation only, no local change)

Locally every JVM runs as one OS user, and the modes stay `0700` and `0600`. The managed directories refuse every group and other bit, so a deployment that runs transaction-service as another user cannot share the folder as it is. Such a deployment chooses object storage with access per service (D-NFR-09), or a shared group along the report read chain together with a matching change of the permission check. That is a deployment decision, made with the deployment; nothing of it is built now.

- **Inbound archive.** The operator's inbound files stay under `<CARDDEMO_VAR_DIR>/inbound/` (section 4.9), which is shared and only read. The archive copies and their `.work/` are under the instance root, so job execution IDs that start again at 1 in a new instance never meet an earlier temporary file (N2).

#### Messages outside the root (ruled 2026-11-11)

Ruled on the privacy review of the folder publication (`55e1e136`, residual R4) and the orchestrator's preference. The rule of section 4.8 (Logs) is extended from the publication and its clean-up to every use of the output root. A path below `CARDDEMO_VAR_DIR` stays in nothing that can be observed outside the `0700` instance root: not in a log line, not in a step's or a job's exit description (`BATCH_STEP_EXECUTION.EXIT_MESSAGE`, `BATCH_JOB_EXECUTION.EXIT_MESSAGE`), so not in the poll answer (section 3) or in Airflow's task log, not in an HTTP problem body, and not in a command's output, with the one exception below. A path can hold a fixed statement's `<acct_id>.pdf` name or any name an extra entry has, and folder paths are the instance root plus IDs, which say nothing that the IDs alone do not.

- **What is carried instead.** For an `OutputRootException`: its code (`code().name()`) and a fixed reason from a closed set that the catching service defines, for example the operation (`ENSURE_DIRECTORY`, `EXISTING_FILE`, `RESOLVE`, `ENSURE`, `FENCE_CHECK`), plus the output kind, the run ID and the job execution ID where the caller has them. For an I/O exception from `java.nio.file` (`NoSuchFileException`, `AccessDeniedException`, `FileSystemException` and the rest, whose messages are paths): the exception's class name only, as `SafeFailures` already does for every other exception. - **Where it is enforced: at the callers, not in `platform/output-root`.** The module's exception messages keep their paths: they are the module's diagnostics, and no caller may pass them on. Backend's API and its messages do not change. The module has a `System.Logger`; if it writes any line itself, backend checks that the line names no path, which is the module's only item under this rule.
  - **batch-service (build-data).** `SafeTasklet` maps an `OutputRootException` to a `CycleJobException` with its code and the fixed reason `step <name> failed: <reason>`, with no cause, instead of copying the message. `CycleExitDescriptions` does the same for an `OutputRootException` that it finds in a failure chain (the fence's check, which runs at the commit outside `SafeTasklet`). Its logs of a failure chain use `SafeFailures`, which keeps class names only. The direct calls the review names (`OutputRoot.ensureDirectory` in `DailyFiles` and in `ExportRejectsTasklet`) need no change of their own once `SafeTasklet` maps them, and the scan below keeps any other path from appearing.
  - **transaction-service (backend).** The report download already logs the run ID and the reason code only (transaction-service.md section 16). Its problem bodies carry the existing code and title, never an exception message, and `ProblemExceptionHandler` never receives an `OutputRootException` or a file-system exception with its message.
  - **db-migrate (backend).** A failure of its output-root step prints the code and a fixed reason, as its SQL failures do (`OUTPUT_ROOT_SQL_FAILED`). **The one exception:** its listing of kept roots, siblings and pre-instance outputs (`kept`) names those folders and their file counts on the operator's console, because the operator removes them by hand (No automatic delete). It names folders only, never an entry inside one, and it is not a log or an API answer.
- **Configured input paths (ruled 2026-11-11, on the source review of `0e1a62a4`).** The rule depends on where a path can be under the allowed configuration, not on where today's values point. `carddemo.data-load.source-dir` (`CARDDEMO_LOAD_SOURCE_DIR`) and `carddemo.batch.pauth.source-file` (`CARDDEMO_PAUTH_SOURCE_FILE`) take any path. Nothing keeps them out of `CARDDEMO_VAR_DIR`, and an operator who stages load files next to the other inputs under `<CARDDEMO_VAR_DIR>/inbound/` is using a valid configuration. So a message never carries the folder or the full path of either setting, absolute or as configured, and an allowlist reason of the form "not below `CARDDEMO_VAR_DIR`" is not accepted for a configured path. Instead the message names the setting and the file's own name, for example `acctdata.txt not found in carddemo.data-load.source-dir` and `<name> not found (carddemo.batch.pauth.source-file)`. One name is not a path: the load files have fixed names, and the unload's name is the last name the operator chose, as the daily file's messages already name its file. No start check is added, and neither setting gains a restriction. Tests (build-data): with the sentinel `CARDDEMO_VAR_DIR` above, each setting pointed below it at a missing file: the exit descriptions, the captured log and `make load`'s output name the setting and the file name, and never the sentinel. The scan's allowlist loses the entries `SourceFile.java path dir`, `LoadPendingAuthorizationsTasklet.java path call .getParent(` and `path file`.
- **Tests (each owner, with its code).** Each test runs with a `CARDDEMO_VAR_DIR` whose own name holds a sentinel, so that every path below it holds the sentinel. batch-service: an `OutputRootException` from `DailyFiles`' and `ExportRejectsTasklet`'s `ensureDirectory` (a `0755` folder), a fence check with the wrong instance (`OUTPUT_ROOT_MISMATCH`), a publication failure and a `NoSuchFileException` in a step: the poll answer, both `EXIT_MESSAGE` columns and the captured log hold the code and the reason and never the sentinel. transaction-service: a download refused by `existingFile` and by the staging folder: the problem body and the log hold no sentinel. db-migrate: a failed output-root step prints no sentinel. A source scan in batch-service fails on `getMessage()` or `toString()` of an `OutputRootException` and on string concatenation of a `Path` into a log call or an exception message, outside an allowlist that names each permitted site.

#### 4.10.2 Shared interface: `platform/output-root`

The new module `platform/output-root`, package `org.carddemo.platform.outputroot`, uses only the JDK (`java.nio.file`, `java.sql`, `java.security`). db-migrate, batch-service and transaction-service depend on it. No Python copy exists: the listings are printed by db-migrate.

Backend publishes the concrete API, with exact signatures, as its hand-off before any other owner codes against it. The orchestrator settled its names on 2026-11-11:

| Name | What it does |
|:--|:--|
| `Instance` | The identity: the exact `DB_NAME()` value and the lower-case instance UUID. Building one checks both forms. |
| `varDir` | Resolves `CARDDEMO_VAR_DIR`: absolute check, legacy-setting check, `toRealPath()`. Fails with `OUTPUT_ROOT_INVALID` or `OUTPUT_ROOT_LEGACY_SETTING`. |
| `read` | Runs the 4.10.1 read on a given connection and returns an `Instance`. A reader that reads the run row instead builds the `Instance` from the same statement (section "Who resolves when"). |
| `root` | Computes `<varDir>/out/<digest>/<uuid>`, with no file-system access. |
| `resolve` | Read-only: validates an existing root (marker, managed paths) and returns it, or reports it missing. Never creates anything. |
| `ensure` | Creates the root atomically (O2) or validates an existing one. |
| `kept` | Lists the other roots, leftover siblings and pre-instance outputs of a database name, with their file counts, for db-migrate's listing. |
| `privateDirectory` | Ruled 2026-11-11 for the staging folder of the report download ([transaction-service.md](transaction-service.md#16-report-download-checks-the-committed-sha256-2026-11-11) item 3.5); not built before its implementation GO; the signature is the one of backend's output-root contract (document v9, section 9.2), the module's only new public method. `privateDirectory(Path base, String... segments)`: the base must be an absolute, existing directory, read with links followed, and is used as given; it is never created, and its owner and mode are not checked (`OUTPUT_ROOT_INVALID` otherwise). There is at least one segment, and each must be one name of the module's segment pattern, not `.` or `..` (`OUTPUT_ROOT_INVALID`). The base's file system must have the POSIX view, and the `unix` view when the process has a uid (`OUTPUT_PERMISSIONS`). Each missing level is created with `createDirectory` and `0700` at creation; a concurrent creation is accepted. Each level, new or existing, passes the module's own path check (`OUTPUT_PERMISSIONS`). An I/O error while a level is created or read is thrown as `UncheckedIOException`. It renames, moves and deletes nothing, and no other method changes. |

`OutputRootException` carries one code from `OUTPUT_ROOT_INVALID`, `OUTPUT_ROOT_LEGACY_SETTING`, `OUTPUT_ROOT_MISMATCH`, `OUTPUT_ROOT_INCOMPLETE` and `OUTPUT_PERMISSIONS`.
Canonical forms (O3):

- **Instance ID:** the lower-case hyphenated UUID, 36 characters, for example `6776d692-7216-4e87-8451-02f9a6772e6f`. SQL Server and the driver render `UNIQUEIDENTIFIER` in upper case, so `of` lower-cases it. The same string is used in the path and in the marker.
- **Database component:** the lower-case hex SHA-256 of the exact `DB_NAME()` value's UTF-8 bytes, 64 characters, with no other part. Every valid SQL Server name is kept, with no business restriction on names, and `/`, `..` and spaces never reach the path. For example, `carddemo` gives `5840ec35206deb1526e4d5157357eb33967810eeaf78b62d08f273555c7cab0d`, and `carddemo_batch_e2e` gives `0f4d4c01b9ed045e253a23586296247326b6070d74139a653767701e7c8861dd`. The full name is in the marker and in db-migrate's listing.
- **Marker:** ASCII, hence UTF-8, exactly three lines, each ending in a single LF, with no BOM and no other whitespace:

  ```text
  carddemo-output-root 1
  database=<name>
  instance=<instance ID>
  ```

  `<name>` is the exact `DB_NAME()` value's UTF-8 bytes in base64url (RFC 4648 section 5, alphabet `A`-`Z`, `a`-`z`, `0`-`9`, `-`, `_`) with no `=` padding. For `carddemo` the second line is `database=Y2FyZGRlbW8`. The number on the first line is the format version; a later format gets a new number. The comparison is on bytes, never on parsed text.
- **Database names accepted:** any non-empty SQL Server `sysname` (at most 128 UTF-16 code units) that is valid Unicode, hence valid UTF-8. There is no ASCII pattern and no guess about file names: the name reaches the file system only as its digest.
#### Tests

The tests run against SQL Server, in `platform/output-root`, db-migrate, batch-service, transaction-service and the scripts. Each case starts the processes from two different working directories. Each case shows what it asserts with file lists and sha256 values taken before and after, not by statement.

- **Canonical forms (O3).** Shared vectors in the module's tests: the two components and the marker line above, the full marker bytes for a fixed identity, and an upper-case driver value, which `Instance` lower-cases. The names `a/b`, `..`, `x y` and a 128-character Unicode name each give a distinct 64-character component and a marker whose name decodes back to the exact name. On a case-sensitive file system (Linux CI), db-migrate, batch-service and transaction-service derive byte-equal root paths for one database.
- **Atomic creation (O2).**
  - A crash is simulated after the marker is written and before the rename. The leftover sibling is listed, and the next `ensure` creates the root.
  - db-migrate and two batch-service starts run at once on a fresh instance. The result is one root, one marker, no sibling of a winner left, and no failure.
  - A root with its `.instance` removed gives `OUTPUT_ROOT_INCOMPLETE` in batch-service, and in transaction-service's download, and is not changed.
  - A non-empty directory created at the root path before the rename makes the rename fail; the helper removes only its sibling and validates that directory's marker (`OUTPUT_ROOT_INCOMPLETE` without one). A plain file at the root path gives `OUTPUT_PERMISSIONS`. A symbolic link at the root path is refused before the rename, and its target is unchanged. In each case nothing at the root path changes.
- **Reset under running services (O1).** With batch-service and transaction-service running, `db-reset`, then report run 1:
  - it never returns the old instance's bytes;
  - no path named by the new instance appears under the old root, and no published path of the old root changes (file lists and hashes before and after);
  - an execution bound before the reset fails at its next fenced transaction with `OUTPUT_ROOT_MISMATCH`.
- **Fresh clone and standalone reader (O6).**
  - On an empty `CARDDEMO_VAR_DIR` and a new `.env`, `make setup` writes the absolute default and prints it. A second run, or a run with another value already set, leaves the value unchanged.
  - transaction-service started before batch-service, and on a test database with no root, serves its views, reports `UP`, and gives the missing-file answer for a download.
  - After batch-service completes a report, the download returns it without a transaction-service restart.
- **Settings and inbound (O5).**
  - A relative `CARDDEMO_VAR_DIR` fails setup without changing the value, and fails every start and the Airflow task with `OUTPUT_ROOT_INVALID`.
  - Each of the four old variables and three old properties, when set, gives a setup `FAIL` line naming it and a start failure `OUTPUT_ROOT_LEGACY_SETTING` naming it.
  - Airflow's `transaction_type_input_present` finds an inbound file from two working directories, and fails instead of returning `False` when the setting is missing.
  - A Makefile run with `CARDDEMO_VAR_DIR` only in `.env` passes that value, not the computed default.
- **Managed paths (O7).** A symbolic link at `out/`, `out/<database component>/`, the root or `.instance`, one owned by another user, or one with any group or other bit (for example a root at `0750` or a marker at `0640`), fails batch-service's start and transaction-service's download with `OUTPUT_PERMISSIONS`, and the mode and owner are unchanged afterwards. A JVM started with `-Duser.name=` set to another name still recognises its own paths. A `CARDDEMO_VAR_DIR` under macOS `/tmp` or `/var` (aliases of `/private/...`) passes.
- **Private test folders (O8).** After `batch_e2e.py` and a JVM test class, the shared `CARDDEMO_VAR_DIR/out/` has no new entry, and the private folder is gone (kept with `KEEP_VAR=1`).
- **Restore (O4).**
  - **Without rotation.** Report 1 completes, then `BACKUP`. Report 2 completes and the database is restored with `RESTORE ... WITH REPLACE`, or, as the review allows, simulated by reseeding `batch.report_run` below the existing output. A rerun of report 2 fails with `PUBLICATION_MISMATCH`, the existing `2/TRANREPT.txt` keeps its hash, and a download of report 2 never returns it. Report 1 still downloads.
  - **With rotation.** After `make db-migrate NEW_INSTANCE=1`, a new root exists, the old root's file list and hashes are unchanged, report 2 runs into the new root, and report 1 gets the missing-file answer.
  - **Clean-up.** A working path whose job execution ID the database does not know survives a start.
- **Two databases in parallel.** The demo and the e2e database each run cycle 1 against one `CARDDEMO_VAR_DIR`. Each writes `rejects/1-1/` under its own root, with no `PUBLICATION_MISMATCH`, and neither root holds a file of the other.
- **Reset with old outputs.** `db-reset` with statements, a report and rejects present passes, and lists the old root with its counts. The old tree is unchanged. In the new instance, report run 1 gives the missing-file answer before its job completes, and the new bytes after it, never the old file.
- **Missing database recreated.** `infra-wipe`, then `db-migrate` with old outputs present, gives the same results as the reset case.
- **Upgrade (O10).** A database migrated up to the version before the marker, with pre-instance outputs, then migrated: it gets a root, the old outputs are listed and unchanged, and an old completed report gets the missing-file answer.
- **Foreign root.** A root whose `.instance` names another ID or another database fails batch-service's start and transaction-service's downloads with `OUTPUT_ROOT_MISMATCH`, and its files are unchanged. transaction-service's start and views are unaffected.
- **No automatic delete.** After every case above, the file list and hashes of every old root, leftover sibling and pre-instance output are unchanged.
- **Marker grants** (backend). A login probe shows that `batch_svc` and `transaction_svc` can read the marker, and that every service login is refused `UPDATE`, `INSERT` and `DELETE` on it.

## 5. Operator rules (`SpringBatchJobOperator`)

| Answer | Operator action |
| :-- | :-- |
| `202` | Defer to the poll trigger with `executionId` (every 10 s). |
| `409 JOB_EXECUTION_RUNNING` | Attach to `executionId` and defer as for `202`. |
| `409 JOB_INSTANCE_COMPLETE`, `exitStatus` `COMPLETED` or `COMPLETED_WITH_REJECTS` | Succeed without relaunching; push `rejectCount` and `outputs` as after a poll. |
| `409 JOB_INSTANCE_COMPLETE`, any other `exitStatus` | Fail, not retryable. |
| `409 JOB_INSTANCE_NOT_RESTARTABLE`, `409 BATCH_WINDOW_REQUIRED`, `409 CYCLE_COMPLETED`, `409 CYCLE_ATTEMPT_CHANGED` (launch, section 2.1), `400`, `401`, `404` | Fail, not retryable (`AirflowFailException`). |
| `503 WINDOW_BUSY` (window open only), `503 LAUNCH_IN_PROGRESS` (close only) | Wait for `Retry-After` and try again, deferred, until the task's `execution_timeout`. These waits do not use task retries. |
| `503 WINDOW_CLOSE_IN_PROGRESS` (launch only) | Wait for `Retry-After` and launch again, deferred. After the close, the launch gets `409 BATCH_WINDOW_REQUIRED` and fails, which is right: the window it needed is gone. |
| any other `5xx`, connection refused, timeout | Retryable through Airflow task retries; the same POST is idempotent. |

Poll results:

- `COMPLETED` with exit `COMPLETED` or `COMPLETED_WITH_REJECTS` is success. `rejectCount` and `outputs` go to XCom, and the reject count goes to the task log. A DAG run note is optional. The operator needs no Airflow API credentials for it.
- Any other terminal result is a task failure.
- Non-terminal with `lease.recoverable: true` fails the attempt as retryable. The task retry re-POSTs the launch, which recovers and restarts. Every operator task therefore has at least 2 retries.

Clearing a task never reruns a completed job: its identity is unchanged, so it gets `JOB_INSTANCE_COMPLETE` and succeeds. A deliberate rerun of a run-keyed job is a new DAG run. A rerun of a cycle is `cycle-rerun` (section 7). Clearing a failed task (for example the purge after the close) restarts that job.

## 6. Batch window

There is one global `WRITES_BLOCKED` window. It is the serialization point between the daily cycle, the reference refresh, the data load and the import. The Airflow pool `carddemo_batch` limits concurrent tasks; it does not keep two DAGs' windows apart.

- **Holders.** A cycle window is opened with `{cycleId}`. Any other window is opened with `{windowRunKey}` = `"<dag_id>/<run_id>"` (the CLI: `"cli/<host>/<timestamp>/<UUID>"`). A V4xx migration adds `ops.batch_window.run_key VARCHAR(250) NULL`, with a check that exactly one of `cycle_id` and `run_key` is set.
- **Open**: `POST /internal/batch-window/open {cycleId | windowRunKey}` returns `200 {windowId, cycleId, windowRunKey, mode: "WRITES_BLOCKED", openedAt}`.
  - It is idempotent for the same holder.
  - A `cycleId` whose cycle is `COMPLETED`: `409 CYCLE_COMPLETED` with the cycle body, not retryable. Only `cycle-rerun` opens a completed cycle's window, inside its own rerun operation (section 7). `open` has no member that skips the check.
  - While another holder's window is open: `503 WINDOW_BUSY` with `Retry-After` (default 60 s) and the open window's members.
  - Writes not drained in time: `503 WINDOW_DRAIN_TIMEOUT`, with the window left closed (retryable).
  - A failed cycle leaves its window open (ERR-JCA7-001). Other DAGs then wait until their `execution_timeout`, which is the signal to the operator.
- **Close**: `POST /internal/batch-window/close {cycleId | windowRunKey, complete}` returns `200 {windowId, cycleId, windowRunKey, closedAt, cycle}` (`cycle` is null for a run-key window).
  - `complete: true` is sent only by the DAG's `close_batch_window`, after every earlier task succeeded. It also sets the cycle `COMPLETED`.
  - `complete: false` is sent by `make -C modernization batch-window-close` after a failure. It reopens online writes and leaves the cycle `OPEN`, so the next DAG run resumes it.
  - `complete` is required for a cycle holder: missing gives `400 INVALID_REQUEST` with `field: complete`. A run-key holder has no cycle, so `complete` may be left out or `false`. `true` gives the same `400`.
  - Closing while an execution of that holder is non-terminal and not recoverable gets `409 EXECUTIONS_RUNNING` with their IDs. Only jobs that need the window count (the list below). A running `purgePendingAuthorizationsJob` never blocks the close. Closing an already closed window returns the same body.
  - A holder for which no window was ever opened: `404 WINDOW_NOT_FOUND`.
  - The close waited for a launch of the holder longer than the lock wait: `503 LAUNCH_IN_PROGRESS` with `Retry-After` (section 9).
- **Which jobs need a window**: every cycle job except `purgePendingAuthorizationsJob` (it writes only `pauth`, which is not covered), plus `dataLoadJob`, `disclosureGroupReloadJob`, `transactionTypeMaintenanceJob` and `importMigrationJob`.
  - A cycle job needs the window held by exactly its `cycleId`. A run-keyed job needs the window held by exactly its `windowRunKey` param.
  - There is no prefix match and no "any open window".
  - `exportMastersJob`, `categoryBalanceListingJob` and `transactionReportJob` need none.
  - `carddemo_import_migration` gets `open_batch_window` and `close_batch_window` tasks, and `make load` opens and closes a CLI window.
- The purge may run after the cycle is `COMPLETED`, identified by `cycleId` and `attempt`.

## 7. Deliberate cycle rerun

`make -C modernization cycle-rerun CYCLE=<id>` refuses while any execution of that cycle is non-terminal and not recoverable. Otherwise it opens the cycle's window and recovers any recoverable executions. It then reverts the cycle's authorization matches ([d33-matching-brief.md](d33-matching-brief.md#batch-steps)), does the restore that [batch.md](batch.md#restart-and-idempotency) describes, supersedes the cycle's completed statement run and invalidates every other unfinished statement run of this and later cycles ([batch.md](batch.md#runs-restart-and-rerun)), raises `attempt` and sets the cycle `OPEN`. The next DAG run therefore creates fresh job instances (`attempt` is identifying). The restore is one transaction that holds the launch lock exclusively and checks again for live executions. Its refusals come in this order: `CYCLE_NOT_FOUND` and a live `EXECUTIONS_RUNNING`; then `WINDOW_BUSY` or `WINDOW_DRAIN_TIMEOUT` when it opens the window; then, after the recovery, in the restore transaction, `LAUNCH_IN_PROGRESS`, `CYCLE_CHANGED`, `DAILY_FILE_CHANGED`, `EXECUTIONS_RUNNING`, `LATER_CYCLE_STARTED`, `WRITTEN_SINCE_SNAPSHOT`, `LATER_STATEMENT_COMPLETED` and `MASTERS_REPLACED_SINCE_SNAPSHOT` ([batch.md](batch.md#data-load-admission-and-the-reruns-refusals-ruled-2026-11-11), which also lists the batch metadata a refused rerun may have changed). On every refusal it tries to close the window again if it opened it. A window it found held stays open, and a close that fails leaves the window open and logs a warning with the close's error code, or its exception class and SQL error number, and no message. On success the window stays open. It never moves or rewrites the inbound daily file: the replacement attempt copies and hashes the inbound file under its own identity when it stages, and the rerun puts a file back only when the inbound file is missing, from the replaced attempt's stored identity ([section 4.9](#49-inbound-daily-file)).

## 8. Superseded rules

The single-instance application lock `carddemo.batch-service` and the startup sweep that marked `STARTED` executions `ORPHANED` (arch commit cba382f) are withdrawn. Several batch-service processes may run against one database: each process recovers only through a launch, and the fence stops a stale owner.
