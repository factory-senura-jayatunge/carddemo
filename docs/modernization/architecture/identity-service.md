## 3. Migration plan for the user-ID family

### What the DDL shows

Checked on `modernization`, `build/data` and `build/backend` (migrations `V001` to `V504`):

- The only foreign key on a user-ID column is `FK_session_user` (`iam.session.user_id` to `iam.app_user.user_id`), and both sides are `iam`. No table outside `iam` references `iam.app_user`. Every other foreign key is on a numeric surrogate (`acct_id`, `cust_id`, `tran_pk`, `daily_pk`, `cycle_id`, job IDs) or on `ref` `type_cd`, whose two ends are both created in `V301`.
- The user-ID columns outside `iam` and the objects that depend on them: `ops.audit.actor_user_id` and `subject_key` (`V004`, `IX_audit_subject`); `core.transaction.created_by` (`V014`); `core.daily_tran.created_by` (`V018`, then `CK_daily_tran_idempotency` and `UX_daily_idempotency` in `V408`, and `core.v_daily_reject` in `V403`, which `V411` recreates); `billpay.payment.paid_by` (`V100`); `batch.report_run.requested_by` (`V407`, `IX_report_run_requester`; `batch.v_report_run_stalled` does not read it); `pauth.auth_detail.fraud_changed_by` (`V500`, with a column-level `UPDATE` grant) and `pauth.auth_fraud.reported_by` (`V501`).

On a fresh database, a migration numbered 203 runs before `V403`, `V407`, `V408`, `V500` and `V501` exist. On an upgraded one it runs after them. So one `V203` for the whole family would either fail on a fresh database, or need "if exists" branches that leave the two paths different. Neither is allowed.

### Rule

A migration may alter a column only when its version is above that of every migration that creates the column or an object depending on it (index, constraint, view, mask, foreign key, column grant). Then the dependencies it drops and recreates are the same on a fresh database and on an upgraded one, and no conditional DDL is needed. A family whose members fall in several ranges is altered per range; this is safe because no foreign key joins members in different ranges. A new user-ID column created from now on is `NCHAR(8) COLLATE Latin1_General_100_BIN2` from the start, and a new foreign key to `iam.app_user.user_id` must use that type.

## 5. User IDs in URLs

Ruling on contract v2's open item (§1, Transport; S31), 2026-11-10. A user ID may hold any character of U+0000 to U+00FF except U+0020 inside, but Tomcat and the Spring Security `StrictHttpFirewall` refuse `%2F`, `%5C`, `%25`, `%3B` and `%00` in a path before any controller runs, and normalise `.` and `..` segments away. Relaxing them (`encodedSolidusHandling`, `setAllowUrlEncodedSlash`, `setAllowUrlEncodedPercent`, `setAllowSemicolon`, `setAllowNull` or a custom firewall) would weaken every service, and narrowing the repertoire would break D-53 and the text repertoire policy. Neither is done. Instead the ID gets a second, URL-safe path form, decided now so that the pilot tests a design instead of waiting for one.

1. **Key form.** `GET`, `PUT` and `DELETE /api/users/key/{userKey}`, where `userKey` is the base64url encoding (RFC 4648 section 5, alphabet `A-Z a-z 0-9 - _`, no padding) of the UTF-8 bytes of exactly the text the plain segment would carry. The service decodes it strictly (padding, characters outside the alphabet, non-zero trailing bits or bytes that are not UTF-8 give `400 INVALID_REQUEST`; more than 1024 key characters the same) and then treats the decoded text exactly as a plain path ID: canonical form (§1 of the contract), the same check order, codes, texts and scenarios. A key is a transport encoding, not a new identifier: it is not stored, logged or audited; logs and `ops.audit` hold the canonical ID, under the log rule of [data-model.md](data-model.md#text-repertoire-and-width).
2. **Plain form stays.** `/api/users/{userId}` keeps working for every ID the server stack lets through, so ASCII callers (scripts, tests, the seed IDs) are unchanged. The two forms are one handler; `/api/users/key/{userKey}` has one more segment, so it never collides with a user whose ID is `KEY`.
3. **Search prefix.** The list takes `startKey` (the same encoding of the typed prefix) as an alternative to `start`; at most one of `start`, `startKey`, `after` and `before` (`400 INVALID_PAGE_REQUEST`). The `firstKey` and `lastKey` cursor tokens use only the base64url alphabet, so they need no escaping.
4. **The page.** The web always uses the key form: it encodes the canonical ID of a list row, or the text typed in the "by ID" entry, as sent, without upper-casing it. Its routes carry the same key: `/admin/users/:userKey/edit` and `/admin/users/:userKey/delete` ([web.md](web.md#routes)). A key the page cannot decode gives the not-found text.
5. **Pilot (S31, extended).** Identity runs it over real HTTP (embedded Tomcat, `RANDOM_PORT`, the production filter chain and firewall) for `ADMIN001`, and for IDs holding NUL, `/`, `%`, `\`, `;`, `?`, `#`, `+`, a C0 control, U+007F, a C1 control (U+0085), tab, U+00A0, `ÿ` and `ß`, and the IDs `.` and `..`: add, list with `startKey`, fetch, update, delete, re-add and sign-on. Through the key form every call must reach the controller and behave as for a plain ASCII ID. Through the plain form, the test asserts the observed result per ID (the ASCII IDs succeed; a refused one gives a `4xx` and changes nothing; `PUT` and `DELETE` on `.` and `..` never reach another handler), so a change in Tomcat or Spring behaviour is seen. No case is skipped. The web adds one Playwright case through the real stack: add a user with `/` and NUL in the ID, find it, edit it and delete it.
6. **OpenAPI and gate.** `web/openapi/identity-service.json` documents both forms and `startKey` only after the pilot passes. List, fetch and delete need `V203`, `V204` and this pilot; add and update keep the gate of section 2.

The contract owner updates contract §1 (Transport), §2 (endpoints), §7 (`INVALID_REQUEST` for a bad key) and S31 to match; [api-security.md](api-security.md) and [mapping.md](mapping.md) list the key form.

## 6. Password hashing

Ruling of 2026-11-10 on the identity pilot's finding. Spring Security 7.1.2's `BCryptPasswordEncoder` throws on `encode` when the password is above 72 UTF-8 bytes, and its `matches` reads only the first 72. D-SEC-07's fixed mode allows 8 to 64 printable characters, counted in code points, with no byte limit: 64 × `é` is 128 bytes and 64 four-byte characters are 256. The 72-byte cap that `PasswordHasher` adds (`MAX_BYTES`) was never approved, and it refused valid passwords with the length text. It is removed; the `NEW_PASSWORD_LENGTH` texts and the 8-to-64 rule stay as they are.

**bcrypt is not binding.** D-04, the user's decision, says "salted hashes (bcrypt or Argon2)". bcrypt was the architecture's pick in D-SEC-03, so changing the encoder is an ordinary compatible change, not a waiver of a user requirement, and no user question is needed.

**Rejected.**

- `{bcrypt-sha256}`, that is bcrypt(base64(SHA-256(password))). The OWASP Password Storage Cheat Sheet calls an unpeppered fast pre-hash a dangerous practice because of password shucking: a SHA-256 of the same password leaked elsewhere can be tested against the stored hash without breaking bcrypt. OWASP's safe pre-hash needs an HMAC whose pepper is kept outside the database. That adds a secret to store and rotate, and rotating it forces every user to reset. Either way it is a construction of our own.
- A byte cap, or passwords limited to ASCII: both narrow D-SEC-07.
- PBKDF2: D-04 does not name it, and OWASP recommends it only where FIPS-140 is required, which no decision asks for.

**Decided.**

1. **Argon2id for every new hash**, through Spring Security's standard `Argon2PasswordEncoder` with OWASP's minimum settings: `new Argon2PasswordEncoder(16, 32, 1, 19456, 2)`, which is a 16-byte salt, a 32-byte hash, parallelism 1, 19 MiB of memory and 2 iterations. `defaultsForSpringSecurity_v5_8()` is not used, because its 16 MiB is below OWASP's minimum. The encoder requires BouncyCastle: `org.bouncycastle:bcprov-jdk18on` is added to identity-service only, with its version pinned in the parent's dependency management.
2. **Existing hashes keep working.** `DelegatingPasswordEncoder("argon2", {argon2, bcrypt: BCryptPasswordEncoder(12)})`. Every new hash gets `{argon2}`: password change, user add and update, seeding, and the one-time hashing of USRSEC passwords at migration. Stored `{bcrypt}` hashes still verify, and no credential changes and no reset is added. Migrated users move to Argon2 at the forced first change that D-04 already requires.

   **Upgrade on successful sign-on (decided 2026-11-10, replaces "no upgrade on sign-on").** Review 118 (I2) found a timing leak. An unknown or locked user costs one Argon2 check (about 16 ms), while a `{bcrypt}` user costs bcrypt(12) (about 220 ms). In fixed mode, the response time therefore tells which sign-on users still have an old bcrypt hash. So when a password verifies against a `{bcrypt}` hash, sign-on replaces it with a new `{argon2}` hash of the same prepared password, in the same transaction as the session. The prepared password is the value that was checked, so legacy mode's upper-cased value stays upper-cased.
   - The write is `UPDATE iam.app_user SET password_hash = @new WHERE user_id = @id AND password_hash = @old`, guarded on the old hash value. One row: the upgrade is done. No row: the hash changed after the check, either because a concurrent sign-on with the same password already upgraded it or because the password was changed. Sign-on then re-reads the stored hash `WITH (UPDLOCK)` in the same transaction and checks the password against it once more. If it matches, the sign-on succeeds with no further write. Otherwise it is refused as a wrong password: the same response body, audit `SIGN_ON_FAILED` with reason `WRONG_PASSWORD`, no session, and no failure counted. Without the re-check, two correct sign-ons of the same `{bcrypt}` user at the same moment would refuse one of them. (Refinement accepted 2026-11-10.)
   - Only the hash changes. `must_change_password`, the audit columns and the sign-on state stay as they are. The upgrade bumps `row_version` once per user, which is accepted: an administrator who opened that user before the user's first sign-on gets one `409`.
   - A `{argon2}` hash is never rewritten on sign-on, and a failed check writes no hash. The Argon2 encode goes through the same semaphore as every hash call (item 5).
   - Residual leak, accepted: a `{bcrypt}` user who has not yet signed on successfully keeps the bcrypt cost on a wrong password. Every hash made from now on is `{argon2}`, including the USRSEC migration's, so only hashes made before this change are affected.
   - The sign-on's audit row is unchanged. A log line says that a hash was upgraded, with the user ID and no hash value.
3. **72 bytes only for old hashes.** A prepared password above 72 UTF-8 bytes checked against a `{bcrypt}` hash is a wrong password, and bcrypt is not called. Such a hash can only come from 72 bytes or fewer, because the encoder refused longer input. The check still spends the time of one hash. Argon2 has no practical input limit.
4. **Same response time.** The dummy hash used for an unknown or locked user is an Argon2 hash.
5. **Memory bound.** Each Argon2 call takes 19 MiB of heap. identity-service runs with `-Xmx256m` on virtual threads, so a burst of sign-ons could exhaust the heap. `PasswordHasher` lets at most two hash or check calls run at once, through a fair semaphore; the other calls wait.
6. **Column width.** `{argon2}$argon2id$v=19$m=19456,t=2,p=1$` plus a 22-character salt, `$` and a 43-character hash is 105 characters, more than `password_hash VARCHAR(100)`. Identity widens the column to `VARCHAR(255)` in `V205__iam_password_hash_width.sql`, which is above `V200` and has no dependent object. The value is ASCII, so the column stays `VARCHAR`. `V205` merges before the encoder change, a schema test checks the width, and the fresh-versus-upgraded catalog comparison of section 3 includes it.
7. **Pilot before merge.** Real encoders, no mocks:
   - The seed `{bcrypt}` hash, and one made from a legacy upper-cased password, still sign on. Afterwards the stored hash starts with `{argon2}` and the next sign-on with the same password works. A wrong password against a `{bcrypt}` hash leaves the hash unchanged. A password change committed between the check and the upgrade (forced by a test hook) makes the sign-on fail with no session, `SIGN_ON_FAILED` `WRONG_PASSWORD` audited and the failure counter unchanged. Two concurrent correct sign-ons of one `{bcrypt}` user (held at the guarded update by a test hook) both succeed, and the stored hash is one `{argon2}` value. The timing check: after the upgrade, the user's wrong-password time is within the spread of an unknown user's.
   - In fixed mode, set and then sign on with: 8 ASCII characters; 64 × `é` (128 bytes); 64 four-byte characters (256 bytes); 64 characters with spaces inside; and a password of 73 bytes. Each one signs on, and the same password with one character changed fails.
   - A password above 72 bytes checked against a `{bcrypt}` hash is refused without calling bcrypt.
   - The stored value starts with `{argon2}$argon2id$v=19$m=19456,t=2,p=1$` and is at most 255 characters.
   - On this laptop: the median and p95 time of one hash and of one check, and 50 concurrent sign-ons under `-Xmx256m` with no `OutOfMemoryError`, with their p95 latency.
8. **Review.** This uses the library's encoder with published parameters and no new construction. It still goes through the normal security review, and the pull request lists the parameters and the pilot's numbers.

The contract owner updates the password rows of the contract. [billpay-slice.md](billpay-slice.md#7-identity-contract), [api-security.md](api-security.md), [data-model.md](data-model.md) and [decisions.md](decisions.md#decided-values) are corrected to match.

## 7. Sign-on state

Ruling of 2026-11-10, decided by the orchestrator under the user's standing delegation and recorded here. `failed_attempts`, `locked_until` and `last_sign_on_at` lived in `iam.app_user`, so every sign-on, good or bad, changed that row's `row_version`. An administrator who had opened a user's edit or delete page then got `409 RECORD_CHANGED` because the user had signed on, although nothing the page shows had changed. D-17 asks for a conflict only when another writer changed the record.

1. **New table, `V206__iam_user_signon_state.sql`** (identity, range V200 to V299, above `V203` to `V205`): `iam.user_signon_state` with `user_id NCHAR(8) COLLATE Latin1_General_100_BIN2` as primary key and `FK_signon_state_user` to `iam.app_user.user_id` with `ON DELETE CASCADE` (the type rule of section 3; users are deleted logically and identity's login has no `DELETE`, so the cascade only acts on a row an operator removes), `failed_attempts SMALLINT NOT NULL` default 0 with a check `>= 0`, `locked_until DATETIME2(3) NULL` and `last_sign_on_at DATETIME2(3) NULL`. It has no `row_version`. The migration copies the three values of every `iam.app_user` row, deleted rows included, then drops `CK_app_user_failed`, `DF_app_user_failed` and the three columns from `iam.app_user`, with anything else that depends on them, under the migration rule of section 3. `R__grants_iam.sql` gives identity's login `SELECT`, `INSERT` and `UPDATE` on the new table and no `DELETE`.
2. **What stays.** `password_hash` and `must_change_password` stay in `iam.app_user`. The user-update page sets the password, so a password change by the user must still make a concurrent administrator update fail with `409`; otherwise the administrator's save would silently overwrite the new password.
3. **Who changes `row_version`.** Only user add, update, delete, re-add and the password change (`POST /api/auth/password`, or a forced change) write `iam.app_user`. Refresh and sign-off never write it. Sign-on writes it only for the one-time upgrade of a `{bcrypt}` hash (section 6, item 2), which changes `password_hash` alone. Otherwise the sign-on path writes only `iam.user_signon_state`, `iam.session` and `iam.audit_event`.
4. **Writes to the state row.** User add, seeding and the USRSEC load insert the state row in the same transaction as the user row. Re-adding a deleted user (section 2, item 1) resets it in the same transaction: `failed_attempts = 0`, `locked_until` and `last_sign_on_at` null. A failed sign-on increments the counter and sets `locked_until` in one atomic `UPDATE ... OUTPUT` on the state row, so two concurrent failures cannot both read 4; success resets it and sets `last_sign_on_at` the same way. If the state row is missing, sign-on treats it as zero failures and inserts it; it never refuses for that reason. The lockout rules and texts of [billpay-slice.md](billpay-slice.md#7-identity-contract) are unchanged.
5. **ETag.** The user-admin `ETag` stays `iam.app_user.row_version`. If the contract's user view shows sign-on state, those fields are read-only and are not covered by the `ETag`.
6. **Tests.** A schema test for the new table and for the dropped columns; the fresh-versus-upgraded catalog comparison of section 3 includes `V206`; scenario S12 (lockout) runs unchanged. New scenario, with `USER0001` holding an `{argon2}` hash (seeding writes Argon2): an administrator fetches `USER0001` and keeps its `ETag`; `USER0001` fails one sign-on and then signs on; the administrator's `PUT` with the kept `ETag` succeeds with `200`. Then the user changes the password and the same `PUT` with the older `ETag` gives `409 RECORD_CHANGED`.

The contract owner updates the data section of the contract and adds the scenario. [data-model.md](data-model.md#inventory) and [billpay-slice.md](billpay-slice.md) are corrected to match.

## 8. Web checks on the sign-on and forced password change pages (2026-11-11)

Ruling on the web's note on `checkPasswordChange` and `checkSignOn` (v1), together with the orchestrator's delegated decisions on the page's mode and the typed user ID.

**The server is authoritative, and the web keeps its checks before submit.** The forced change page (`/sign-on/change-password`, D-SEC-07) keeps running its checks before it calls `POST /api/auth/password`, as it has since D-SEC-07. On every call the server runs its whole order: blanks and input lengths, then authentication of the current password (throttle, lookup, lockout, wrong password), then the new-password rule. The page shows the server's problem exactly as the server sends it, on the server's `field`, even when its own checks predicted something else. These pre-submit checks stay because they read only what the user typed: no stored value, no other call and no new endpoint. So they reveal nothing about the account, they never bypass authentication of the current password, and they cannot let a form through that the server would refuse. With a wrong current password and an invalid new one, the page shows the new-password problem and makes no call. After the user fixes the new password, the server answers with the sign-on failure. That is the accepted sequence. It also spares the user a counted failed attempt for a form that would fail anyway. No call is added to check the current password first.

**The web's checks are the server's static rules, never stricter.** The web runs the server's rules 1 to 4 and 6 to 9 of the note's section 2, in that order, with the same semantics from one shared source (the shared form rules or the shared primitives, whichever backend accepts). After those, it runs the one web-only check: the confirmation, which compares values with trailing U+0020/U+0000 removed. The server prepares the password the same way, so those values store the same password. Rule 5 (throttle, lookup, lockout, wrong password, user type) is server-only. Any web check that refuses a value the server accepts is a defect. **Input caps (corrected 2026-11-11).** No password input on either page has a length cap: the current, new and repeat inputs on the change page and the password on sign-on all lose `maxLength={64}`. That cap counts UTF-16 units, and a valid 64-code-point password such as 33 × U+1F600 must be typable. The shared code-point rules enforce the limits instead. **The user ID input also loses `maxLength={8}` (corrected 2026-11-11), on both pages.** The server accepts a raw ID whose trailing U+0020/U+0000 pad takes it past 8 characters (`"USER0001  "`), and the cap would refuse it. Rule 3 (`INVALID_INPUT_USER_ID`, more than 8 code points after the pad is removed) is a static rule and comes after rules 1 and 2. So the web runs it from the shared source, in that position. If the shared source does not provide it, the web does not check the ID length, and the server answers. The web never narrows the IDs the server accepts. The web's order differs from the server's in one way only, and it is recorded as such for D-SEC-07: new-password problems (rules 6 to 9) can appear before an authentication failure (rule 5), never the reverse. Backend's `differs` kind for `NEW_PASSWORD_SAME` is ratified, and the blank checks that do not depend on the mode are one shared form for both pages. The mock gets the same rules, so its tests stay truthful. The note's section 5 vectors are approved as the parity tests. Its open question 6 is answered by this paragraph and the one above.

**Mode on the forced change page.** The page is public. `/api/features` requires a session and is not opened to anonymous callers. Reaching the page with the `PASSWORD_CHANGE_REQUIRED` route state from sign-on proves fixed mode, because the server sends that answer only when DEF-SGN-011 is fixed. On that path the page runs the full fixed-mode checks above. When the page is entered without that state (typed URL, reload, bookmark), the mode is unknown. The page then runs only the checks that do not depend on the mode: the three blank checks (`USER_ID_REQUIRED`, `PASSWORD_REQUIRED`, `NEW_PASSWORD_REQUIRED`, where blank means only U+0020/U+0000) and the confirmation. It then submits the raw values, and the server decides. No legacy form of the rules is built, because no caller needs one.

**The typed user ID is passed raw.** Sign-on passes the user ID to the change page, through the route state or `pendingPassword`, exactly as typed. The change request sends it exactly as typed too. Today's `userId.trim().toUpperCase()` changes `é` and `ÿ` and must go: only the server makes a user ID canonical. The web normalizes a copy only to compare (`NEW_PASSWORD_IS_USER_ID`: trailing U+0020/U+0000 removed, then `legacyUpper` on both sides) and to display.

**Sign-on page (`checkSignOn`): scoped fix.** Its two blank checks use the server's blank rule, so only U+0020/U+0000 count as blank. `"\t"`, U+3000, NBSP and U+FEFF are sent to the server, and a password made only of NULs gets `PASSWORD_REQUIRED`. Its password input has no length cap (see "Input caps" above). The web adds rule 3 (`INVALID_INPUT_USER_ID`) and rule 4 (`INVALID_INPUT_PASSWORD`, more than 64 code points after the trailing pad is removed), both of which the server already applies, in the server's order. Nothing else in sign-on changes: the order is VAL-SGN-001 then VAL-SGN-002, as in COSGN00C, and the server makes the decision.
